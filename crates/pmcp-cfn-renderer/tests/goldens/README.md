# Semantic-golden corpus

Generated by `scripts/generate-cfn-goldens.sh` (one-time, LOCAL, needs
Node — never runs in CI). Each `*.golden.json` embeds its own inputs
(`descriptor_toml`, `params`) plus the `support::normalize`-d expected
output (`normalized`), so the harness (`tests/semantic_golden.rs`) never
needs Node, `cdk`, or network access — it only needs the checked-in JSON.

`tests/semantic_golden.rs`'s `all_goldens_match_renderer_output` reads only
`tests/goldens/*.json` (non-recursive) — files under `pending/` are
deliberately invisible to it. A golden lands in `pending/` when the
resource-family module it needs hasn't been implemented yet; it moves up to
`tests/goldens/` (and the harness's `#[ignore]` for that family, if any,
comes off) in the plan task that implements that family.

## Corpus reality vs. the original design doc

`docs/superpowers/specs/2026-07-21-cfn-renderer-extraction-design.md` §7
assumed "19 tracked fixture descriptors" in THIS repo. That count is real —
but the 19 live in the sibling `pmcp-run` repo
(`built-in/*/servers/*/.pmcp/deploy.toml`), not here. This repo has exactly
ONE tracked `.pmcp/deploy.toml`: `crates/pmcp-server/.pmcp/deploy.toml`.
Since every golden file embeds its own descriptor text, this doesn't affect
CI self-containment — it only changes where Task 2 drew the corpus from.

## Inventory

### Generated (primary corpus — fresh `cargo pmcp deploy init` scaffolds)

One project per resource-family variant, scaffolded from scratch via
cargo-pmcp's own scaffolder (the parity target — `cargo-pmcp/src/commands/deploy/init.rs`),
then `npx cdk synth`, re-synthesized with a **fake** account
(`123456789012`) and region (`us-east-1`) so no real AWS account number is
ever committed (see the script's header comment for the credential-context
mechanism).

| File | `target.type` | auth | Exercises | Status |
|---|---|---|---|---|
| `plain-lambda.golden.json` | `pmcp-run` | disabled | `lambda`/`logs`/`outputs` (Lambda-only stack, no API Gateway; CDK's own default execution role + the pmcp-run composition IAM sugar) | **Active** — Task 3's TDD driver |
| `pending/http-api.golden.json` | `aws-lambda` | disabled | `http_api` (`HttpApi`/`Integration`/`Route`/`Stage`, `Lambda::Permission`) on top of the plain-Lambda shape | Pending Task 5 |
| `pending/oauth-cognito-dcr.golden.json` | `aws-lambda` | `cognito` (`--oauth cognito`) | `cognito` (`UserPool`/`UserPoolResourceServer`/`UserPoolDomain`) + `dynamodb` (the DCR `ClientsTable`) + a 3-Lambda/authorizer `http_api` shape | Pending Task 6 |

`oauth-cognito-dcr` covers BOTH "OAuth/Cognito" and "DCR" from the brief's
four named variants (plain Lambda, HTTP API, OAuth/Cognito, DCR) as a
SINGLE fixture: the scaffold bundles Dynamic Client Registration
unconditionally into its Cognito OAuth stack (there is no
Cognito-without-DCR or DCR-without-Cognito scaffold option) — see
`create_oauth_stack_ts` in `cargo-pmcp/src/commands/deploy/init.rs`.

### Wild (secondary corpus — real fixture from the sibling `pmcp-run` repo)

The sibling `pmcp-run` repo (read-only for this crate; never written to) is
where the design doc's "19 tracked descriptors" actually live
(`built-in/*/servers/*/.pmcp/deploy.toml`). The generation script copies
ONLY `.pmcp/deploy.toml` + `deploy/{lib,bin,cdk.json,package.json,
tsconfig.json}` (never the checked-in `cdk.out/` — that would embed
`pmcp-run`'s REAL AWS account number) into a scratch dir and re-synthesizes
locally with the same fake account as the generated corpus.

| File | Source | Exercises | Status |
|---|---|---|---|
| `pending/wild-msr-vtt.golden.json` | `pmcp-run:built-in/sql-api/servers/msr-vtt` | `iam` (`[[iam.statements]]` — 4 real custom grants: Athena workgroup access, Glue catalog/database/table metadata, S3 read, S3 read/write for Athena query results) on top of the plain-Lambda (`pmcp-run` target) shape | Pending Task 4 |

## Regenerating

```bash
# Optional: point at a different pmcp-run checkout (defaults to
# ../pmcp-run relative to this repo's root).
export PMCP_RUN_REPO=/path/to/pmcp-run

./scripts/generate-cfn-goldens.sh
```

Needs `node`/`npm`/`npx`, `jq`, `cargo`, and the `aws` CLI (used only as a
harmless no-op — see the script's header comment). Never run in CI.

## Cross-crate publish coupling (release sequencing)

The `[auth.cognito]` field promotion (Task 2) extended `pmcp-package`'s
closed set — bumped to **0.1.1** on this branch. The published `0.1.0`
REJECTS `[auth.cognito]`-bearing descriptors (`deny_unknown_fields`), so
`pmcp-package 0.1.1` must publish **before or with** `pmcp-cfn-renderer`
(Task 10 wires the order into release.yml + CLAUDE.md item 13/13a).
