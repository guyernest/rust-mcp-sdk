<objective>
Enforce the required v2 HTTP headers (`Mcp-Method`/`Mcp-Name`, alongside `MCP-Protocol-Version`) on the streamable-HTTP path, driven by the SAME `_meta`-resolved v2 signal Plan 04 threads (one negotiation mechanism, not two): reconcile the header vs `_meta` version (fail closed on disagreement), strict 4xx reject when `Mcp-Method`/`Mcp-Name` are absent on a v2 request (D-05), header/body method cross-check as an anti-smuggling fail-closed gate (D-06), and outbound emission — all HTTP-only and v1-untouched. Every NEW header-violation error this plan emits sources its JSON-RPC error code from Plan 03's `error_codes::` table (VERS-06), so this plan does not reintroduce bare literals even as it adds new error paths.

Purpose: VERS-05 is exactly what the official conformance suite (Phase 118) will test; lenient-now would mean a breaking tightening later. Critically, Plan 04 already resolves era from per-request `_meta` on ALL transports (D-11); if this plan judged "is this v2" from a raw header independently, a request could get v2 dispatch via `_meta` while bypassing header enforcement (or vice versa) — RESEARCH Pitfall 2's "two negotiation mechanisms colliding". So the v2 determination here MUST be Plan 04's resolved signal, and header-vs-`_meta` disagreement is a fail-closed reject mirroring D-06. Headers exist only on HTTP; stdio v2 is header-free (D-11). And because the checker's VERS-06 blocker requires ALL error codes to resolve from one table, this plan's new error paths use `error_codes::` from the outset (Plan 08 migrates the file's pre-existing 25 literals).
Output: `MCP_METHOD`/`MCP_NAME` constants; unified v2-signal reconciliation + strict inbound validation + body cross-check + outbound emission in `streamable_http_server.rs`, with new error codes from `error_codes::`, routed and tested through the HTTP path (not in-memory transport), with a proptest over the untrusted header/body cross-check.
</objective>
