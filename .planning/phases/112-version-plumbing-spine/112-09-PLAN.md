<objective>
Close verification Gaps B and C from `112-VERIFICATION.md`: the per-request `_meta`/`ProtocolContext` spine is wired for `tools/call` ONLY. Generalize `extract_request_meta_value` to read `_meta` from `GetPrompt` and `ReadResource`, and thread the resolved `protocol_context` + `request_meta` into the `RequestHandlerExtra` built inside `handle_get_prompt`/`handle_read_resource` at BOTH native dispatch sites (`core.rs` and `mod.rs`), mirroring the existing `handle_call_tool` pattern. This single root-cause fix simultaneously:
- makes `extra.era()`/`.client_info()`/`.trace_context()` return the resolved context inside prompt AND resource handlers (VERS-01, VERS-03, VERS-09);
- feeds the HTTP header gate a correct v2 `_meta` signal so a compliant v2 `prompts/get`/`resources/read` is accepted instead of 400 (VERS-05, Gap C);
- lets the already-generic `inject_v2_result_envelope` fire `resultType`/`serverInfo` for those two methods (VERS-07).

Purpose: the phase's headline claim — "ProtocolContext resolved once at ingress is threaded through dispatch to EVERY handler" — is currently false for 2 of the 3 documented name-bearing methods. This restores it without any new machinery: the resolver, envelope injector, and header classifier are all already generic; only their INPUT (`extract_request_meta_value`) and the two handlers' `extra` construction are incomplete.

Output: generalized `extract_request_meta_value` + protocol-context/request-meta threading at four handler sites (core.rs ×2, mod.rs ×2), with unit + proptest coverage, live HTTP prompts/get + resources/read v2 acceptance tests, and golden v1 byte-identity fixtures for both methods.

**Scope note (v1 byte-identity):** Adding `.with_request_meta(..)`/`.with_protocol_context(..)` populates the in-memory `RequestHandlerExtra` ONLY; it does not touch the wire response. `inject_v2_result_envelope` remains gated on `era==Era::V2` (None on v1/non-opted-in), so v1 output stays byte-for-byte identical. This must be proven, not assumed (golden fixtures below).

**Scope note (wasm):** the wasm32 `RequestHandlerExtra` is the zero-field stub at `src/server/mod.rs:162`; `core.rs`/`mod.rs` dispatch are `#[cfg(not(target_arch = "wasm32"))]`. This plan is native-only; the sole wasm obligation is that `cargo build --lib --target wasm32-unknown-unknown` stays green.
