<objective>
Close CR-01 on the surface the change request originally missed: the curated single-call HTTP path,
which is the default, JS-engine-free build.

Purpose: `HttpClient::substitute_path` (`http/client.rs:143-163`) does
`path.replace(&placeholder, &value_str)` with no character check and no percent-encoding, and
`render_scalar` returns any `String` verbatim. The identical injection exists here with no Code Mode
involved. Scoping D4 to `code_mode.rs` alone — as the change request first drafted — would have
closed the class for script and Code Mode tools while leaving the lightest, most common build open.

Output: declared placeholder rules carried on `Parameter`, the D4 check in `substitute_path`'s
neighbourhood calling the one core primitive, and a test binary that proves the two JS-engine-free
CR-01 probes on a build that has no `openapi-code-mode`.
</objective>

In `substitute_path`'s loop, between `render_scalar` returning the rendered string and
`path.replace(&placeholder, &value_str)`, call
`pmcp::server::schema_validation::validate_path_placeholder(&param.name, &value_str,
&param.placeholder_rules())` and map a `PlaceholderRefusal` into `HttpConnectorError::Backend`. Order
matters and must be preserved: the refusal happens BEFORE any substitution is applied to the path
that will be sent, so a refusal on the second of two placeholders cannot leave a partially-substituted
URL anywhere.

**Then, at the END of `substitute_path` after every `replace` has run, call
`pmcp::server::schema_validation::validate_resolved_path(&path)`** and map its refusal the same way.
Three of the review lanes converged on the need for a post-substitution check here, and it buys two
things on this surface specifically: a segment-length bound on the composed result, and refusal of a
residual `{` or `}`. The second is a real open case Gemini and Fable both found —
`substitute_path` SKIPS a parameter absent from `args` (`client.rs:157-160`, `if let Some(value) =
args.get(...)`), so the literal `{name}` stays in the path and is sent upstream. D1's `required` only
refuses when the `ParamDecl` says `required = true`, while `build_operation` marks Operation path
parameters required INDEPENDENTLY (`tools.rs:511-516`) — so the two disagree and a template placeholder
with no supplied argument currently reaches the backend as braces. `validate_resolved_path`'s
residual-brace rule closes it in one place for both surfaces rather than adding a second bespoke check.

Name the parameter ONLY in the refusal for the missing-value case, per the `render_scalar` convention —
never the path, and never the partially-substituted template.

Gate both calls `#[cfg(feature = "input-validation")]`. Under a build without the feature the function
behaves as today — record that in a comment right there, and record in the same comment that
`input-validation` is in the toolkit's `default` (plan 03) so the unenforced path is an explicit
opt-out rather than an accident.

Message wording must match `render_scalar`'s house style exactly: name the declared parameter, state
the declared expectation, never the value. The two surfaces differ only in error type
(`HttpConnectorError::Backend` here, `ExecutionError::RuntimeError` on the Code Mode side), and a
caller must not be able to tell from the text which surface refused.

Extend `substitute_path`'s `# Errors` rustdoc with the new refusal kind, naming
`validate_path_placeholder` as the enforcing function — this is a threat-comment-discipline
obligation, not decoration: the acceptance rows in task 3 are what make the claim checkable.

Add unit tests in this file's test module for the floor behaviors below, plus one asserting that a
placeholder-free template is untouched.
