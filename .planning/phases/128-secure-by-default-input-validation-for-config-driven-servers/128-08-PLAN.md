<objective>
Complete D4(b) on the Code Mode surface — the spec-declared narrowing — and pin the floor-then-narrow
ordering as a property rather than as a handful of fixtures.

Purpose: plan 05 moved placeholder resolution ahead of dispatch and added a default-implemented
`placeholder_rules` hook because `PlanExecutor` has no access to an OpenAPI document. The only
component that does is the executor implementation, and `HttpCodeExecutor` does not carry the parsed
schema today — it holds a client, a base URL, an auth provider and a per-request token. This plan
gives it the schema and overrides the hook.

Output: `HttpCodeExecutor::with_schema`, the `placeholder_rules` override, the binary wiring, and a
property-test binary asserting the D-10 ordering and percent-encoding closure over generated input.
</objective>

(1) Add `schema: Option<std::sync::Arc<crate::http::OpenApiSchema>>` to `HttpCodeExecutor`, defaulted

(2) Override `HttpExecutor::placeholder_rules(&self, method: &str, path_template: &str, param: &str)`
on `HttpCodeExecutor`: look the operation up with `OpenApiSchema::operation_for(path_template, method)`
— an O(1) index hit, because the index is keyed on `(path, METHOD)` (`http/schema.rs:145-152`) — find
the parameter by name, and return that `Parameter`'s `placeholder_rules()`.

**The `method` parameter is what makes this an index lookup rather than a linear scan or a wrong
answer.** Plan 05's trait method now carries it (all three lanes reached this independently). Without it
the only options were scanning `self.operations`, or matching on path alone and silently narrowing a
`DELETE` with a `GET`'s declared constraints.

When there is no schema, no matching operation or no matching parameter, return the default — and state
in the doc that the default is still floored and capped, so the unconditional protections survive a
miss and only the spec's ADDITIONAL narrowing is lost. That sentence is the difference between a safe
default and a silent hole, and a reviewer will look for it. Write it that way and not as "a miss
weakens nothing", which is the phrasing (2b) corrects.

(2b) **State honestly what a template-spelling MISS costs, and add the config-time guard that bounds
it.** Codex's finding: looking up the script's exact template and returning the default on a miss means
`/users/{alias}` misses a spec declaration for `/users/{id}` while resolving to the SAME endpoint, so
the declared `pattern` silently disappears — and calling that "weakens nothing" is inaccurate. The floor
and the cap do remain, which is what the phrase was reaching for, but the SPEC NARROWING is lost and
that is a real reduction for a caller who relied on it.

What this plan does about it, in three parts:

  - **Correct the wording.** The override's rustdoc says: a miss retains the unconditional floor and the
    always-on cap, and LOSES the spec's narrowing. Do not write "weakens nothing".
  - **Log a miss once per (method, template) pair** at `tracing::debug!` — naming the method and the
    template, never a value. A silent narrowing loss is the "an enforcement that is off must never read
    as on" prohibition applied to a partial enforcement, and a script whose template drifted from the
    spec is an operator-fixable condition that currently produces no signal at all.
  - **Add a `lint()`-level guard for the CONFIGURED case.** A `[[scripts]]` or curated tool whose
    template does not match any spec path, when a spec IS present, is an author error the operator can
    fix before deploy — coordinate with plan 03's `ServerConfig::lint()` and add a finding for it.
    Note the bound on this guard, and state it: it covers templates written in the CONFIG. A template
    a Code Mode script composes at runtime cannot be checked at config time, which is why the
    debug-level miss log exists as well.

Do NOT attempt template canonicalization or fuzzy matching — Codex's other suggestion. Normalizing
`{alias}` to `{id}` requires knowing they denote the same parameter, which only the spec's own path can
say, and a canonicalizer that guessed wrong would narrow from the WRONG parameter's rules, which is
worse than not narrowing. Recorded in the dispositions ledger.

(3) The override must build `PlaceholderRules` and hand them to the core primitive. It must not
evaluate a pattern itself — there is exactly one regex path in this phase and it is
`compile_input_2020_12`, which is what guarantees that a placeholder pattern and an `inputSchema`
pattern resolve the whitespace shorthand identically.

(4) Unit tests: an executor with a schema returns the spec's declared pattern for a declared path
parameter; an executor without a schema returns the default; an unknown operation or unknown
parameter returns the default; and `allow_slash` is false on every spec-derived result (D-11).
  </action>
  <behavior>
