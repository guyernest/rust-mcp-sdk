## Planner decisions recorded in this plan

- **Q2 — where does `validate_path_placeholder` live? CORE `pmcp`, in `server::schema_validation`,
  re-exported from `pmcp-code-mode`.** D-09 says "export it from `pmcp-code-mode`", but RESEARCH
  Finding 6 measured that the toolkit's `http` feature list
  (`crates/pmcp-server-toolkit/Cargo.toml:112-124`) contains no `pmcp-code-mode` edge, so the curated
  single-call build cannot reach a `pmcp-code-mode`-exported helper without either a new dependency
  edge that widens the curated graph (and that the purity gate bans in some served trees,
  `Makefile:1642`) or two copies of one security rule — the drift class this repo has already been
  bitten by (`output_validation.rs:667-691`). Core is the only home both surfaces already depend on:
  the toolkit pins `pmcp` unconditionally (`Cargo.toml:23`) and `pmcp-code-mode` pins
  `pmcp = ">=2.2.0"`. D-09's published-helper obligation is met by a `pub use` re-export in
  `pmcp-code-mode` (plan 05), so a third-party `HttpExecutor` implementor still reaches it by the name
  D-09 names.
- **Q3 — is a bare `%` refused? YES, narrowly.** D-10 names "percent-encoded forms of these" but
  `%252e` double-decodes to `.`, so an encoded-form denylist alone is bypassable. The rule adopted:
  refuse `%25` in any hex case outright (this closes the whole double-encoding family in one check),
  and refuse any `%` not followed by two ASCII hex digits (a malformed escape has no legitimate use in
  a path-placeholder value). Ordinary well-formed escapes such as `%20` still pass the `%` rule and
  are then caught by the case-insensitive denylist if they decode to a denied character. This is a
  DEVIATION from the change request's literal wording and is recorded as such in the rollout note
  (plan 10).
