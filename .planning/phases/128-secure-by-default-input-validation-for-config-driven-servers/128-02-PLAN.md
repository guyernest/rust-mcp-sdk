## Planner decisions recorded in this plan

- **Q2 — where does `validate_path_placeholder` live? CORE `pmcp`, in `server::schema_validation`,
  re-exported from `pmcp-code-mode`.** D-09 says "export it from `pmcp-code-mode`", but RESEARCH
  Finding 6 measured that the toolkit's `http` feature list
  (`crates/pmcp-server-toolkit/Cargo.toml:112-124`) contains no `pmcp-code-mode` edge, so the curated
  single-call build cannot reach a `pmcp-code-mode`-exported helper without either a new dependency
  edge that widens the curated graph (and that the purity gate bans in some served trees,
  `Makefile:1642`) or two copies of one security rule — the drift class this repo has already been
  bitten by (`output_validation.rs:667-691`). Core is the only home both surfaces already depend on:
  the toolkit pins `pmcp` unconditionally (`Cargo.toml:23`) and `pmcp-code-mode` pins
  `pmcp = ">=2.2.0"`. D-09's published-helper obligation is met by a `pub use` re-export in
  `pmcp-code-mode` (plan 05), so a third-party `HttpExecutor` implementor still reaches it by the name
  D-09 names.
- **Q3 — is a bare `%` refused? YES, narrowly.** D-10 names "percent-encoded forms of these" but
  `%252e` double-decodes to `.`, so an encoded-form denylist alone is bypassable. The rule adopted:
  refuse `%25` in any hex case outright (this closes the whole double-encoding family in one check),
  and refuse any `%` not followed by two ASCII hex digits (a malformed escape has no legitimate use in
  a path-placeholder value). Ordinary well-formed escapes such as `%20` still pass the `%` rule and
  are then caught by the case-insensitive denylist if they decode to a denied character. This is a
  DEVIATION from the change request's literal wording and is recorded as such in the rollout note
  (plan 10).

`e.instance_path()`.** The first draft of this plan said the pointer "comes from `e.instance_path()`,

`ValidationError` was ever `Display`-formatted, which is the specific leak this module was built to
avoid. This is the highest-severity finding against this plan and it is a real hole, not a
re-litigation.

`fn safe_pointer(e: &jsonschema::ValidationError<'_>, schema: &Value) -> String`:

  - Walk the instance pointer segment by segment. A segment is emitted VERBATIM only when it is a
    DECLARED property name — that is, when the corresponding position in `schema` reaches it through a
    `properties` map key (or, for an array index, when the segment parses as a base-10 integer, which
    carries no caller-chosen text).

    schema construct where the KEY came from the instance rather than from the declaration — is
    replaced by a fixed redaction token. Use one token, documented, and never include the key's length
    or a hash of it: a length is a side channel on a value that may itself be PHI.

    locked count-plus-allow-list message and it never names a key at all.
  - Doc the helper with the measured counterexample above, so a future contributor reading
    "instance_path is safe for declared properties" understands the missing qualifier.

  - `pub fn validate_path_placeholder(param: &str, value: &str, rules: &PlaceholderRules<'_>) -> Result<(), PlaceholderRefusal>`
    executing exactly four ordered steps, with the ordering's rationale in the function doc:

    1. UNCONDITIONAL FLOOR, which no pattern can relax (D-10). Implemented as **DECODE ONCE, THEN
       DENY ON THE DECODED FORM** — not as an enumerated denylist of literal and pre-encoded spellings.
       Two reviewers independently found that an enumeration is incomplete by construction: a mixed
       form such as `.%2E` or `%2E.` decodes to the parent-directory sequence while matching neither
       the literal nor the fully-encoded spelling in the list. Enumerating more spellings does not
       converge; decoding does. Steps, in order:

       (1a) Refuse `%25` in any hex case OUTRIGHT, before decoding (Q3). This is what makes
       "decode once" sufficient rather than a first round of an unbounded regress: with `%25`
       refused, no surviving input can encode a further `%`, so one decode pass reaches ground truth.
       (1b) Refuse any `%` not followed by two ASCII hex digits — a malformed escape has no legitimate
       use in a path-placeholder value, and leaving it undecided would mean deciding whether to treat
       it as a literal `%` or as an error at every downstream layer.
       (1c) Percent-decode the value ONCE, ASCII-case-insensitively over the hex digits (`%2e` and
       `%2E` decode identically; a case-sensitive `contains` is a bypass).
       (1d) Apply the denylist to the DECODED bytes. Refuse an empty original `value`. Refuse `?`,
       `#`, NUL, **backslash**, **carriage return**, **line feed**, and any other ASCII control
       character (0x00-0x1F and 0x7F). Refuse `/` unless `rules.allow_slash` is true. Refuse the
       parent-directory sequence with NO escape even when `allow_slash` is true (D-11). Refuse a
       decoded value that is exactly a **single dot**.

       The four additions beyond the first draft's list are each motivated, not defensive padding:
       **backslash** because IIS, some nginx rewrite configurations and AWS API Gateway normalize
       `\` toward `/` and `..\` toward traversal, so a floor that stops `../` and passes `..\` is
       surface-dependent rather than sound; **CR and LF** because an unencoded newline in a path
       reaching a logging or transport layer is response-splitting and request-smuggling surface, and
       this value is attacker-chosen text; **the other control characters** because admitting some and
       not others invites exactly the enumeration gap this step exists to avoid; and **the single
       dot** because `.` is a path segment with meaning (`a/./b` normalizes to `a/b`), so two adjacent
       placeholders each holding `.` compose to `..` — which is the composition case step 5 and
       `validate_resolved_path` exist to catch, and refusing the single dot closes it at the value
       level as well.
    2. ALWAYS-ON CAP (D-08): refuse when the value exceeds `PLACEHOLDER_MAX_LENGTH`, counted in
       Unicode code points via `chars().count()` so it agrees with `jsonschema`'s `maxLength`
       semantics (RESEARCH Finding 1d measured that `maxLength` counts code points).
    3. DECLARED PATTERN NARROWS (never replaces). When `rules.declared_pattern` is `Some(p)`, build the
       one-property schema `{"type":"string","pattern":p}` and evaluate it through
       **`cached_input_validator`, NOT `compile_input_2020_12` directly**, so a placeholder pattern and
       an `inputSchema` pattern resolve `\s` through the identical engine AND a repeated pattern is
       compiled once. Codex and Fable both found that the first draft named the uncached compile entry
       point while T-128-10's mitigation column claimed memoization — so as specified, every
       placeholder check on every request would compile a fresh regex, which is both a per-request cost
       and a direct amplifier of the ReDoS residual the same threat row accepts. The distinction
       between compiling and caching is an explicit in-tree architecture point
       (`output_validation.rs:595-605`); name the cached entry point so the claim and the code agree.
       A pattern that does not compile is itself a refusal with `rule = "pattern"` and a value-free
       message; the cache stores that failure too, so a broken declared pattern is not recompiled per
       request either.
    4. DECLARED LENGTH NARROWS FURTHER: the effective cap is the minimum of `PLACEHOLDER_MAX_LENGTH`
       and `rules.declared_max_length`. A declared length LARGER than the constant never widens it.

  - `pub fn validate_resolved_path(path: &str) -> Result<(), PlaceholderRefusal>` — **the
    COMPOSED-path check, and the answer to the single most consequential review finding against this
