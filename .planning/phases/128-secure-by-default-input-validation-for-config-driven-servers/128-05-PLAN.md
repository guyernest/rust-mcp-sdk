## FORK 2 — SC-4 and the layer-1 `${var}` route. DECIDED: extend this plan to floor layer 1.

The first version of this plan stated that layer-1 `PlanExecutor::resolve_path` must be
byte-identical after the change, and moved only layer-2 `{key}` resolution ahead of dispatch. Codex
and Fable independently found that this leaves SC-4 unmet, and the finding verifies exactly:

- `PathTemplate::parts` includes `PathPart::Variable(String)` and `PathPart::Expression(ValueExpr)`
  (`crates/pmcp-code-mode/src/executor.rs:356-365`).
- The JS compiler emits those parts for a template literal: a bare identifier becomes `Variable`
  (`:1968`), anything else becomes `Expression` (`:1972`).
- `PlanExecutor::resolve_path` pushes the stringified value **straight into the path with no check**
  (`:3151-3170`: `result.push_str(&shared_json_to_string_with_mode(value, JsonStringMode::Json))` for
  the `Variable` arm and the same for the `Expression` arm).

So a Code Mode script writing `` api.get(`/search/${v}`) `` with `v = "2026AA?string=<payload>"` never
touches a `{key}` placeholder, never enters layer 2, and is never floored. Code Mode scripts are
model-authored — that is the untrusted path this phase exists to close — so "closed on BOTH HTTP
surfaces" would have been false as planned.

**Decision: extend, do not amend SC-4.** The orchestrator considered amending SC-4 honestly and
rejected it, and the reason is the phase's own identity: this phase exists to correct three false
security claims in `tools.rs`. Shipping SC-4 with a known open route would be a fourth instance of the
exact defect class the phase was created to fix. That is not an available option.

**Design consequence — per-value checks are insufficient by construction, so the floor must be applied
at BOTH granularities.** Two individually-legal values compose into an illegal path: `"."` and `"."`
across adjacent placeholders yield the segment `..`, and 180 plus 200 code points yield a 380-code-point
segment over the cap. The composed result is then parsed as a URL at
`crates/pmcp-server-toolkit/src/http/client.rs:389`, which is where a composed traversal becomes a
different endpoint. Therefore:

1. Every dynamic CONTRIBUTION is floored where it is produced — each layer-1 `Variable` / `Expression`
   rendered string, and each layer-2 `{key}` rendered value — through `validate_path_placeholder`.
2. The COMPOSED path is checked once, after both layers have run and before dispatch, through
   `validate_resolved_path` (plan 02). This is the only check that can see a composition, and it runs
   after a decode-once normalization so `.%2E`-style mixed encodings cannot slip between the two
   layers.

Both are Task 2's work, both are acceptance criteria, and Task 3 adds a composition probe whose whole
point is that each of its two values passes the per-value check.
