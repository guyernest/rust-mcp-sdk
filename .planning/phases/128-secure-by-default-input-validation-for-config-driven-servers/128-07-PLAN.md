## Planner decision recorded in this plan — Q5, and the deviation it creates

**Q5 — how does SC-3's deploy-time warning reach `cargo-pmcp`? Route B PLUS the literal D-07
surface.** RESEARCH priced four routes. Route C (re-implement the lint locally) is rejected outright:
two copies of a security rule is the drift class this repo has already been bitten by. Route D
(descope) fails SC-3. Route A (put it inside `validate deploy` only) muddies a command whose
contract is specifically about IAM. So:

- The PRIMARY surface is a new `cargo pmcp validate config` subcommand with clean semantics. This is
  a **DEVIATION from SC-3's wording**, which names `cargo pmcp validate deploy` verbatim, and from
  the ROADMAP text; plan 11 records it in the rollout note and amends the ROADMAP success criterion.
- D-07 is a LOCKED decision and names `cargo pmcp validate deploy` explicitly, so `validate deploy`
  ALSO emits the findings — as warnings, when a toolkit `config.toml` is discoverable next to the
  deploy config. This preserves the command's documented contract ("a failing `validate deploy`
  guarantees a failing `deploy`", `validate.rs:36-38`) because a lint finding never fails it.

**Release-ledger consequence, for plan 11.** This adds an EIGHTH `pmcp-server-toolkit` pin to the
workspace — `cargo-pmcp` is already the most-pinned crate in the tree (CLAUDE.md item 15a) and this
pin must move on every future toolkit release. It also makes `cargo-pmcp` itself part of this
release: a new subcommand is a feature, so 0.24.3 -> 0.25.0, taking D-13's "~11 crate versions" to
twelve. Both facts go in the release note. Incidentally, CLAUDE.md item 15a records `cargo-pmcp` at
0.23.0 and it is actually at 0.24.3 (RESEARCH Finding 7a) — plan 11 corrects that ledger line while
it is there.

## Flagged assumptions — unresolved probe edges carried forward

The deterministic edge probe surfaced one **unclassified** edge against SC-3. Per the probe protocol
an unclassified row is never auto-resolved and never silently dropped; it is carried here as an
explicit flagged assumption for a human to close:

- **SC-3 · unclassified.** The probe could not classify one aspect of "an uncapped string parameter is
  surfaced by `ServerConfig::validate` and by `cargo pmcp validate deploy`". The unresolved question
  is what "surfaced" obliges when the two surfaces disagree — specifically, whether a config that
  lints clean under the toolkit version `cargo-pmcp` is BUILT against may still lint dirty under the
  toolkit version the deployed server RUNS, and what the operator is owed in that case. This plan
  pins both surfaces to one implementation at build time, which makes them agree for a
  same-version pair and says nothing about a mixed-version pair. Not resolved here; surfaced for a
  human decision. Do not treat the pinning as a closure of it.
