<objective>
Ship the two escape hatches, so no team has to wrap or fork toolkit internals for a rule a schema
cannot express — and make the enforced-rule set visible in deploy logs.

Purpose: E1 covers rules about what may LEAVE the server (PHI policies, endpoint allowlists, per-session
budgets); E2 covers rules about combinations of values (a parameter required only when another has a
particular value, code-list lookups, normalization). With both, the UMLS server drops its hand-written
`ValidatingTool` and `OutboundGuard` and keeps only a short PHI policy — which is the concrete outcome
the change request's evidence section asks for.

Output: a `RequestPolicy` trait hooked into both HTTP surfaces before auth, a per-tool
`ArgumentValidator` running after D1, builder registration for both, the once-at-startup enforcement
log, an integration binary and the toolkit example.
</objective>

## Flagged assumptions — unresolved probe edges carried forward

The deterministic edge probe surfaced two **unclassified** edges, one against E1 and one against E2.
An unclassified row is never auto-resolved and never silently dropped; both are carried here as
explicit flagged assumptions for a human to close:

- **E1 · unclassified.** The probe could not classify one aspect of "`RequestPolicy` runs after D1/D4
  on every outbound backend request". The unresolved question is what "every outbound request" obliges
  for request shapes this phase does not enumerate — a retry (the curated client retries up to three
  times, `http/client.rs:43-51`/`:290`), a redirect followed by `reqwest`, and a Code Mode script's
  50th call within one `tools/call`. This plan invokes the policy once per logical outbound request at
  the seam before auth, which answers the retry case only by where the hook sits. Not resolved;
  surfaced for a human decision, and deliberately adjacent to the deferred per-request time-budget
  phase, which is where the retry semantics are being decided.
- **E2 · unclassified.** The probe could not classify one aspect of "per-tool `ArgumentValidator`,
  attachable by tool name from Rust". The unresolved question is what a validator is entitled to DO
  besides refuse — the change request lists normalization among its typical uses, which implies
  mutating the arguments before dispatch, and a mutating validator has a different contract
  (idempotency, ordering against D1, and what the tool's declared schema then describes). This plan
  ships a REFUSE-ONLY validator taking `&Value` and says so in the trait documentation. Not resolved;
  surfaced so the normalization case is decided deliberately rather than by the shape of a first
  signature.
