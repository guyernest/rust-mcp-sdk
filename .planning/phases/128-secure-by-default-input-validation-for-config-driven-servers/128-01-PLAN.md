## Planner decisions recorded in this plan

RESEARCH.md left seven open questions to the planner. Three are decided here; the other four are
decided in the plans that own them (Q2/Q3 in plan 02, Q5 in plan 07, Q7 in plan 03).

- **Q1 — does `format` enforce? YES.** `format` is annotative in jsonschema 0.49.2 (RESEARCH
  Finding 1g: `"!!!not-a-uri!!!"` validates `true` under `draft202012::new`). A config keyword that
  silently does nothing is the same defect class as the three false `T-*` comments SC-6 exists to
  fix, so inputs compile through a dedicated format-asserting builder
  (`jsonschema::options().with_draft(Draft::Draft202012).should_validate_formats(true).build(&schema)`).
  Because that changes compile semantics, inputs get their OWN compile entry point and never share
  `output_validation::compile_2020_12`'s validator — which is also what D-02 requires (inputs bypass
  `compile_for_era`'s two arms).
- **Q6 — which cache? A SEPARATE input cache, keyed on schema text alone.** Q1 forces it: a
  format-asserting validator must not collide with a non-asserting output validator under the same
  `(Era, String)` key. Two further reasons: `Era` is deliberately not an input parameter (D-02), so an
  `Era`-keyed cache would be a lie; and a per-handler `OnceLock<Arc<jsonschema::Validator>>` in the
  toolkit was REJECTED because it would put a `jsonschema` 0.49 type in `pmcp`'s public API, making
  every future `jsonschema` bump a breaking `pmcp` change. `validate_input` takes and returns only
  `serde_json` and `pmcp` types; the cache is internal.
- **Q4 — `pmcp-code-mode-derive` bumps as a PATCH (0.3.0 -> 0.3.1).** Decided here because it changes
  what plan 10's release set contains. Its `pmcp-code-mode` pin is in `[dev-dependencies]`
  (`crates/pmcp-code-mode-derive/Cargo.toml:25-27`), it emits no `HttpExecutor` code, and a
  path-carrying dev-dep is stripped at publish time — so the published artifact is unaffected by
  D-09. A patch keeps the workspace resolving after the dev-dep repin to `"0.6"` AND keeps root
  `Cargo.toml:264`'s `^0.3.0` valid under the CLAUDE.md caret exception, so `:264` does NOT move
  (the pin D-13 missed is thereby resolved by not needing to move). Reasoning goes in the release note.

## Deviations from the source documents, stated rather than worked around

- **The CR says `input-validation` is "forwarded from `default`". It is not** — the toolkit's
  `default = ["code-mode"]` (`crates/pmcp-server-toolkit/Cargo.toml:93-102`). Adding it is a task,
  scheduled in plan 03 together with the two `default-features = false` consumers it would otherwise
  miss. This plan wires the feature; it does not yet turn it on by default.
- **The toolkit's own `jsonschema` optional dependency is removed**, not kept. D-01 says core owns the
  one validator path; leaving a second `dep:jsonschema` edge in the toolkit is the parallel-validator
  D-01 rejects. `input-validation` becomes `["pmcp/schema-validation"]`.
