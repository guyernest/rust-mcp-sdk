(1) `fuzz/fuzz_targets/fuzz_input_schema_enforcement.rs`: a libfuzzer target that splits the input
using the SAME length-prefixed layout `fuzz_schema_draft_pin.rs` documents — a selector byte, a
little-endian u32 schema length, the schema bytes, then the instance bytes as the remainder. The
degeneracy argument that motivated that layout applies identically here: splitting raw bytes at an
arbitrary point makes both halves fail to parse as JSON on nearly every iteration, and a
hand-writable layout is what makes a committed seed corpus possible.

**The invariant must be stated by PROVENANCE, not by string absence — the naive oracle produces false
failures.** The first draft asserted that the refusal contains no byte-subsequence of the instance and
none of the instance's object keys. Codex found three ways that rejects legitimate output:

  - a DECLARED key such as `cui` is intentionally echoed when its value violates `maxLength` — the
    refusal names the declared property, which is what SC-7 requires;
  - the `additionalProperties` message intentionally lists the ALLOWED names, which are declared keys;
  - an independently generated schema and instance can legitimately contain identical strings by
    coincidence, and a fuzzer explores exactly that space.

So the oracle is: **generate a unique sensitive SENTINEL that cannot appear in the declaration, place it
in the instance, and assert the sentinel never appears in the refusal.** Concretely:

  - Derive the sentinel from the fuzz input's own bytes so it varies per case, but constrain it to a
    shape no generated SCHEMA can contain (for example a fixed rare prefix plus a hex encoding of a
    counter). Verify the sentinel is absent from the serialized schema before asserting anything; if it
    is present, skip the case rather than fail — a collision is a generator artifact, not a defect.
  - Place the sentinel in both positions the phase cares about: as a VALUE, and as an UNDECLARED KEY
    (the PHI-shaped-key case, `{"Jane Doe DOB 1970-01-01": 1}`).
  - Assert the sentinel appears nowhere in `render_refusal`'s output, on bytes rather than `char`
    boundaries.
  - Distinguish declared keys from unexpected/dynamic keys explicitly: a key present in the schema's
    `properties` MAY appear in the refusal; a key matched only by `additionalProperties` or
    `patternProperties` MUST NOT. Generate schemas of BOTH shapes, because plan 02's `safe_pointer`
    redaction is what makes the second case safe and this target is its durable guard.
  - Treat plan 02's fixed redaction TOKEN as permitted output — read its exact value from
    `128-02-SUMMARY.md` rather than reinventing it, or the oracle will flag the redaction itself.

Copy the header discipline verbatim in structure: the run incantation with `+nightly`, why nightly is
required, the explicit warning not to cite `make test-fuzz` as evidence for this target, what is being
fuzzed and why, the input layout diagram, and — new — a paragraph stating why the oracle is
sentinel-based rather than absence-based, so a future contributor does not "simplify" it back into the
false-failure form.

**Use an UNCACHED validate path, or bound the cache.** Codex's second finding: this target calls the
public `validate_input` over CHANGING schemas, and plan 01 caches compiled validators in a process-global
`Mutex<HashMap<String, ...>>` keyed on schema text — so a long fuzz run grows the map without limit
until the process dies of memory rather than of a real counterexample. The existing output validator
separates uncached compilation from caching for precisely this fuzz/property hazard, and says so in its
own doc comment (`src/server/output_validation.rs:598-605`). Mirror that: add a `fuzzing`-gated
uncached seam in `schema_validation` (the shape of `output_validation`'s `fuzz_support` module, which
`fuzz_schema_draft_pin` already uses) and have this target call THAT rather than the caching entry
point. Record in the SUMMARY which seam was added and that the target uses it, because a target that
OOMs is indistinguishable from a target that found nothing.
