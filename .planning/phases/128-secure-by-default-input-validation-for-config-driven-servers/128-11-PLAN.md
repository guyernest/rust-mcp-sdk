## FORK 1 — the release-order deadlock. DECIDED: exit (b). Recorded as a deviation.

This is the single most consequential decision in the phase and the one the review lanes disagreed
about. The user was asked and chose "let the planner decide and record it", so it is decided here, in
full, with its rationale — not left open and not deferred to execution.

### The deadlock, stated precisely

Four facts, all re-verified against the tree at planning time:

1. Root `Cargo.toml:263` is `pmcp-code-mode = { version = "0.5.3", path = "crates/pmcp-code-mode" }`,
   and it sits inside `[dev-dependencies]` (the section opens at `:242`). It carries **both** `path`
   and `version`. Cargo strips a dev-dep from the published manifest only when it carries NO version
   requirement; one that carries a requirement is RETAINED and must resolve on crates.io while
   `cargo publish -p pmcp` prepares and verifies the manifest. Root `:264` is the same shape for
   `pmcp-code-mode-derive = { version = "0.3.0", path = ... }`.
2. **That, and not a `code-mode` feature, is why `pmcp-code-mode` publishes before `pmcp`.**
   `release.yml` publishes `pmcp-code-mode` at `:195`, `pmcp-code-mode-derive` at `:213` and `pmcp` at
   `:231`. There is NO `code-mode` entry in root `[features]` — grep returns only the two dev-dep
   lines and the workspace-members list. CLAUDE.md item 2's recorded rationale attributes the order to
   `pmcp`'s "own `code-mode` feature", which does not exist; correcting that prose is Task 2's job
   (see below), because a documented mitigation whose stated mechanism is wrong is the same defect
   class as this phase's P0 sub-goal.
3. `crates/pmcp-code-mode/Cargo.toml:29` is
   `pmcp = { version = ">=2.2.0", path = "../../", default-features = false, features = ["logging"] }`.
   Plan 05 adds `features = ["schema-validation"]` to it, because the `pub use` of
   `pmcp::server::schema_validation::{...}` (Q2) is how D-09's published-helper obligation is met
   without a second copy of the placeholder rule.
4. Every publish step in `release.yml` tolerates ONLY an "already exists" failure
   (`if echo "$OUTPUT" | grep -q "already exists"`); anything else is `exit 1`, which strands every
   later step. A "no matching package" or "does not have these features" failure at `:195` therefore
   publishes **nothing** from this phase.

Put together: if `pmcp-code-mode` publishes first while requiring a `pmcp` that carries
`schema-validation`, its verify build resolves the highest PUBLISHED `pmcp` — 2.20.4 — which has no
such feature, and the job dies at the first step. And `pmcp` cannot publish first, because root's
retained dev-deps make `cargo publish -p pmcp` require an on-crates.io `pmcp-code-mode` and
`pmcp-code-mode-derive`. Neither can go first. **No reordering alone resolves it.**

### Why exit (a) is not available

Exit (a) — leave code-mode's `pmcp` requirement alone and change no release mechanics — reads as free,
and it is not. Note first that `>=2.2.0` is an open-ended lower bound and DOES admit 2.21.0, so the
requirement VALUE is not itself the blocker; the blocker is that at `:195` the highest published
`pmcp` is 2.20.4. So exit (a) can only work by removing the `features = ["schema-validation"]` edge —
which means `pmcp-code-mode` cannot reach `pmcp::server::schema_validation` at all. That leaves three
sub-options and each breaks a LOCKED decision:

- a local copy of the placeholder floor inside `pmcp-code-mode` — forbidden by the "a security rule
  must never exist in two copies" prohibition carried by plans 02, 05, 06 and 08, and by the
  three-way-drift incident (`output_validation.rs:667-691`) that prohibition records;
- the floor behind a non-default `pmcp-code-mode` feature — forbidden by the "a validation rule must
  never be silently disabled by a feature flag being off" prohibition, and it would leave the DEFAULT
  code-mode build with no floor, which is the shipped configuration;
- the floor back inside the toolkit's `HttpCodeExecutor` — this re-creates the blind-decorator defect
  D-09 exists to fix, and D-09 is locked.

An exit that requires breaking a locked decision is not an exit. **(b) is the only route that keeps
D-09, Q2 and the no-second-copy rule simultaneously true.**

### Exit (b), as implemented here

Make root's `pmcp-code-mode` **and** `pmcp-code-mode-derive` dev-deps **path-only** — drop the
`version` key from both — and then publish `pmcp` ahead of them. Both must move: `:264` is the same
retained-dev-dep shape as `:263`, so leaving it would keep `cargo publish -p pmcp` blocked on an
unpublished `pmcp-code-mode-derive 0.3.1`.

This is not a novel pattern in this repository. It is the CR-01 pattern already applied **four lines
below**, at root `Cargo.toml:266-270`, for `pmcp-agent` — whose in-tree comment states this exact
reasoning ("A `version` key here would therefore make every `cargo publish -p pmcp` fail on an
unresolvable dev-dependency. Cargo strips path-only dev-deps at publish time"). CLAUDE.md item 9b
records the same pattern for `crates/pmcp-openapi-server`, with the measured failure it prevents. The
new entries get a comment in that same house style, naming Phase 128 and the deadlock.

### Gemini's P0 is REJECTED, and the distinction matters

Gemini's fix was "reorder `release.yml` to publish `pmcp` before `pmcp-code-mode`", standalone, with
root's dev-deps untouched. **That is wrong and would break the release**: `cargo publish -p pmcp`
would then run while `pmcp-code-mode 0.6.0` and `pmcp-code-mode-derive 0.3.1` are unpublished, and
both are retained in `pmcp`'s published manifest — so the job would die at the `pmcp` step instead of
the code-mode step, having published nothing. Gemini also cited CLAUDE.md items 1-5 as evidence that
`release.yml` "was out of sync"; CLAUDE.md item 2's own correction note says the opposite, that the
workflow was right and the prose was wrong, and that reordering the workflow to match the prose would
reintroduce the class of bug PR #303 fixed.

The reorder appears in exit (b) as a CONSEQUENCE of the path-only change, not as the fix. The
path-only change is the prerequisite that makes it safe, and it is the part Gemini did not identify.
Codex was correct that the plan as specified is unsatisfiable but did not reach the resolution; Fable
was correct that the order is load-bearing as it stands and did not notice that raising the
requirement invalidates that.

### Reversibility, and what guards it

`one-way`. Root `Cargo.toml`'s published manifest changes shape, and `release.yml`'s order is a
published release mechanic that CLAUDE.md names as THE AUTHORITY. Guards landing in the same commit:

- a tripwire test asserting root's `pmcp-code-mode` and `pmcp-code-mode-derive` dev-dep entries carry
  NO `version` key, in the shape of `crates/pmcp-openapi-server/tests/pmcp_package_pin.rs`'s
  `pmcp_package_dev_dep_is_path_only` (CLAUDE.md item 9b), so a future contributor "restoring a pin"
  fails a test rather than a release;
- an extension to `scripts/check-release-coverage.sh` asserting that `pmcp`'s publish step precedes
  `pmcp-code-mode`'s, so the new order is machine-checked exactly as D-10's `pmcp-package` order is,
  and a revert to the old order is a build failure rather than a discovery.

Both are Task 1's work and both are acceptance criteria.
