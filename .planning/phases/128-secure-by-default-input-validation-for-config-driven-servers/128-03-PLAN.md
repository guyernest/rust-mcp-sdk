<objective>
Grow the parameter vocabulary the declared schema needs, and make a forgotten `max_length` fail safe
instead of open — without refusing the free-text body parameters that work today.

Purpose: D2 gives config authors `pattern` / `min_length` / `format` / `items` / `max_items` so a
code-list parameter can be expressed as a rule rather than as a hope; D3 applies a hard default cap
in path and query position (where a long value has no legitimate use and where CR-01 lives) and a
warning in body position (where review note C's objection stands). SC-2 moves a bad `pattern` from a
call-time 500 to a config-time refusal.

Output: six new `ParamDecl` fields, a `[server.validation]` section, position-scoped cap emission,
`ServerConfig::lint()`, four new `ConfigValidationError` variants, and the Q7 default-on rollout
across three manifests.
</objective>

## Planner decisions recorded in this plan

- **Q7 — does `input-validation` go into the toolkit's `default`? YES, plus two explicit adds.**
  RESEARCH Finding 8c measured that the toolkit's `default = ["code-mode"]` does not contain it, so
  the change request's "forwarded from `default`" is a task rather than a fact. Adding it is the
  mechanism by which the CR's whole compatibility story ("the defaults ship on") actually happens.
  `pmcp-sql-server` (`Cargo.toml:33`) and `pmcp-openapi-server` (`:47`) inherit it automatically;
  `pmcp-workbook-server` (`:43`) and `pmcp-workbook-compiler` (`:107`) set
  `default-features = false` and would silently miss it, which would contradict D1's "every
  config-declared tool", so both name it explicitly.
- **D-07's "warns" is delivered by a NEW `lint()`, not by `validate`.** RESEARCH Finding 11a measured
  that `ServerConfig::validate` is first-error-wins `Result<(), ConfigValidationError>` with no
  warning channel at all, so D-07's wording is unexpressible in that signature as it stands. A
  separate `pub fn lint(&self) -> Vec<ConfigWarning>` is additive, leaves `validate`'s 15 existing
  unit tests untouched, and gives plan 09's CLI something to call that is not entangled with
  boot-time validation. `[server.validation] strict = true` is what promotes a lint finding into a
  `validate` error. This is a DEVIATION in mechanism, not in outcome, and is recorded in the rollout
  note.
- **D-15's forward-incompatibility note must cover `[server.validation]`, not only `ParamDecl`.**
  RESEARCH Finding 10d measured that `ServerSection` (`config.rs:328-333`) and `ServerConfig`
  (`:100-102`) both carry `#[serde(deny_unknown_fields)]`, so a config carrying `[server.validation]`
  fails to parse on 0.1.3 exactly as a `pattern` does. Plan 10 carries the CHANGELOG entry; this plan
  records the fact in the `ValidationSection` rustdoc.

(1) `config.rs`, `ParamDecl` (`:913-949`): add six `#[serde(default)]` fields — `pattern:
Option<String>`, `min_length: Option<u64>`, `format: Option<String>`, `items: Option<ItemsDecl>`,
`max_items: Option<u64>`, and `allow_slash: bool`. Doc each one. Three doc comments carry measured
facts that a config author cannot discover otherwise:

  - `pattern`: it is UNANCHORED, per JSON Schema. A rule written as a bare character class matches any
    substring and therefore buys no enforcement; anchor it. Also state the two-engine split: a plain
    pattern routes to the linear `regex` engine whose whitespace class is a partial ECMA-262 set that
    does not include U+3000, while a pattern containing a lookaround or a backreference routes to
    `fancy-regex 0.18` where the whitespace class is exactly the Unicode `White_Space` property —
    so adding a lookahead silently changes what the whitespace shorthand means, and a
    security-relevant rule should spell out an explicit character class instead of using the
    shorthand.
  - `format`: it IS enforced on inputs in this SDK (Q1), through an input-only format-asserting
    builder, and it is NOT enforced on outputs. Say so; the default `jsonschema` behaviour is
    annotative and a reader who knows that will otherwise assume this field is decorative.
  - `allow_slash`: D-11 — the ONLY legitimate source is this explicit per-parameter opt-in. An OpenAPI
    spec's `allowReserved` must never be wired to it.

Also add three variants:

  - `EmptyParamPattern { tool, param }` — refusing `pattern = ""`, because an empty pattern matches
    everything and is a likely author error.
  - `NonFiniteParamBound { tool, param }` — refusing a `minimum`/`maximum` that is non-finite or whose
    magnitude exceeds 2^53, since `ParamDecl` stores them as `f64` (`config.rs:942`) and a larger

    and cannot catch**, because Codex found the stated guarantee is stronger than the check: by the
    time the value is an `f64`, `9007199254740993` has ALREADY rounded to `9007199254740992`, so an
    `abs() > 2^53` test on the parsed value cannot see that it was rounded. Two honest options; take
    the first if it is cheap and the second otherwise, and record which in the SUMMARY:
    (i) inspect the RAW TOML value before it becomes `f64` — `toml::Value::Integer` preserves `i64`,
    so a magnitude check there is exact — which requires reading the bound through a custom
    `Deserialize` or a pre-pass over the parsed TOML;

    rounded before this check ran, so `minimum`/`maximum` are not a safe way to bound a 64-bit integer
    ID. Say that in the variant's rustdoc and in the `maximum` field's rustdoc, so an author reaching
    for a `u64` bound learns the limit instead of trusting a silently-rounded number. Gemini reached
    the same limitation from the author's side (a `u64` ID above 2^53 cannot be bounded at all), so
    documenting it discharges both findings.

`ServerSection` and `ServerConfig` both carry `deny_unknown_fields`, a config carrying this section
fails to parse on toolkit 0.1.3.

(2) `config.rs`: add `pub enum ParamPosition { Path, Query, Body }` and
`impl ToolDecl { pub fn param_position(&self, param_name: &str) -> ParamPosition }`. Derivation,
stated in the doc comment as a coupling requirement: a name that appears as a `{name}` segment of
`self.path` is `Path`; otherwise, for a tool that is a single-call HTTP tool (both `path` and
`method` present), every other declared parameter is `Query`; everything else — SQL named binds,
script tool arguments — is `Body`. This is the SAME rule `tools.rs::build_operation` applies when it
splits `path_param_names` from the remaining query parameters; the doc must say so and say that a
divergence silently mis-scopes the cap.

**One correction to that rule, found by Gemini: a mutating single-call tool's non-path parameters are
NOT query parameters for D3's purposes.** `build_operation` (`tools.rs:517-526`) marks every
non-path declared parameter `ParameterLocation::Query` — that is its historical behaviour and it stays
— but D3's position scope is about where a long value is DANGEROUS, not about which
`ParameterLocation` enum the operation carries. On a `POST`, `PUT` or `PATCH` tool an author declaring
a payload field such as `comment` or `body_text` would otherwise receive a hard 256-code-point cap,
which is exactly the free-text breakage review note C objected to and D-05 exists to avoid. So:

  - if the parameter appears as a `{name}` segment of `self.path` -> `Path`;
  - else if `self.method` is present and is `GET`, `HEAD` or `DELETE` (methods whose non-path inputs
    genuinely travel in the query string) -> `Query`;
  - else if `self.method` is present and is `POST`, `PUT` or `PATCH` -> `Body`;
  - else -> `Body`.

Document the divergence explicitly: `param_position` and `build_operation` agree on PATH position,
which is the coupling that matters for D4, and they deliberately differ on the query/body split for
non-path parameters on mutating methods, because one is answering "where does this travel" and the
other "where is length dangerous". State that in the doc comment, because a maintainer comparing the
two functions will otherwise read the difference as a bug and "fix" it into the breakage. Add a unit
test asserting a `POST` tool's non-path string parameter is `Body` and receives NO default cap, and one
asserting a `GET` tool's is `Query` and does receive it.

Also document, in the `ParamPosition::Query` arm, that a `GET` tool's non-path string parameters are
capped at the configured default in code points — Gemini's second suggestion, and the thing an author
whose search tool starts refusing long queries needs to find.
