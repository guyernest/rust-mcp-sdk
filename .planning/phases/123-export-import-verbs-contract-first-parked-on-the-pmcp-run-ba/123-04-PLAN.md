<objective>
Write down the one thing the SDK and the pmcp.run platform must agree on byte-for-byte, in the one
place both sides read, and back it with fixtures that cannot lie.

`pull` consumes a tar the PLATFORM produces. Plan 01 built the reader and the writer; this plan
records the CONTRACT they implement, so the platform's implementer has a normative statement rather
than an SDK binary to reverse-engineer. D-12 puts the rule in `pmcp-package` (the format crate both
sides reference) while keeping the `tar` dependency out of it — 122 D-13's allowlist exists precisely
so that adding `tar` to the format crate is friction, and the friction is the feature.

Purpose: the fixtures are the enforcement. Prose alone drifts; a checked-in tar authored INDEPENDENTLY
of `write_tar` catches a writer that quietly stops conforming, which a fixture regenerated from that
writer could never do. That provenance rule — *checked-in bytes, never regenerated from the writer
under test* — is the property adopted from the platform exchange (handoff §3.2) and the whole reason
this fixture is worth having.

Output: a normative `# Artifact tar framing` docs section in `crates/pmcp-package/src/oci/mod.rs`, a
new `artifact_tar_v1/` fixture directory holding one conformant and several hostile tars with a
provenance header, and `cargo-pmcp/tests/package_artifact_framing.rs` binding the two.

Runs in Wave 2 alongside plan 03; the two share no files.

**C-6 / C-7, so they are not rediscovered:** `pmcp-package` is workspace-EXCLUDED (it carries its own
`[workspace]` table), so root `cargo fmt/clippy/test` do not reach it. Every change here is verified
through `make pmcp-package-gate`, which uses `--manifest-path` and asserts a nonzero test count. And
this plan deliberately adds NO public API and NO dependency, so no version bump and no nine-emitter
lockstep is triggered — Phase 124 owns the release half.

Add a `# Artifact tar framing` section to `crates/pmcp-package/src/oci/mod.rs`'s module documentation,
immediately adjacent to the existing description of the layout it constrains.

Write it as a NORMATIVE statement addressed to two implementers — this SDK and the pmcp.run platform —
not as a description of what `cargo-pmcp` happens to do. It is the one place the two sides must agree
byte-for-byte, and the platform produces the tar `pull` consumes.

**State each rule as a requirement, with its reason:**

- **Entry inventory.** Exactly three shapes are legal: the layout marker file at the archive root,
  `index.json` at the archive root, and `blobs/sha256/<hex>` where `<hex>` is exactly 64 lowercase
  hexadecimal characters. Nothing else. An unrecognized path shape is a refusal, not something to skip.
- **No wrapper directory.** `index.json` is at the archive root. A leading component such as a package
  name is a refusal. Reason: the reader must be able to identify entries without guessing a prefix.
- **No absolute paths, no parent-directory components.** This is the zip-slip defence stated at the
  contract level. Say plainly that untarring attacker-controlled bytes is a traversal surface and that
  the defence belongs in the rule, not only in one implementation. Note additionally how the SDK's own
  reader makes traversal unrepresentable rather than filtered — it never writes an archive-supplied
  path, deriving every destination from a digest it computed — and recommend the same to any
  implementer, while keeping the path prohibition normative for those who do not.
- **Regular files only.** Symlinks, hardlinks, directory entries, fifos and device entries are all
  refusals. A symlink is an escape primitive; a directory entry is unnecessary because the three legal
  paths imply their structure.
- **No duplicate paths.** A repeated path is a refusal, never last-wins. Two entries claiming one path
  is an authoring bug or an attack, and merging lets a hostile writer shadow a real entry.
- **Uncompressed.** The artifact is a plain tar. §5.1 names no compression, and adding one creates a
  decompression-bomb surface for no stated benefit. Record this as an SDK ASSUMPTION awaiting platform
  confirmation, cross-referencing the question written into `contracts/pmcp-run/portability-v1.graphql`
  — do not state it as a settled fact about the platform.
- **Reproducible headers.** Entry headers are normalized — zero mtime, zero uid and gid, empty user and
  group names, a fixed regular-file mode — and entries appear in a fixed order: the layout marker,
  then `index.json`, then every blob sorted lexicographically by hex. Consequence, stated: packing the
  same layout twice yields byte-identical archives, so the artifact can be compared, cached and
  digested by transport machinery without spurious differences.
- **The layout marker.** MEASURED and worth stating because §5.1 is silent: nothing in this crate ever
  READS the marker file — a grep of the crate's sources finds only the write, doc comments, and one
  test read-back. So the rule is: emit it on write (a plain extraction then yields a valid layout for a
  human debugging by hand), accept it on read, ignore its content, and always regenerate it through
  `OciLayout::create`. Do NOT require it on read, so an implementation that omits it still
  interoperates. Also record this as an open question to the platform: whether their reader tolerates
  the extra entry.

**Fixture provenance, stated in the rule itself.** Name the fixture directory by path, and state the
rule adopted from handoff §3.2: fixtures are CHECKED-IN BYTES, NEVER REGENERATED FROM THE WRITER UNDER
TEST. Explain why in one sentence — a fixture produced by the code it tests is a tautology and cannot
detect the drift it exists to detect.

**State the boundary this section deliberately does not cross.** This crate holds the RULE; the CODEC
lives in `cargo-pmcp`. That split exists so no archive dependency enters this crate's resolved graph,
which is machine-enforced by the crate-local dependency allowlist Phase 122 landed. Say so, so the
next reader does not "tidy up" by moving the reader in.

Do NOT add a validator function, a predicate, a type or any other public item. Prose plus fixtures
only. A dependency-free predicate over path/length pairs is a defensible follow-on but is a public API
addition, which drags in the nine-emitter version-bump lockstep for no gain in this phase — record it
as a clean follow-on in the SUMMARY rather than building it. Do NOT edit
`crates/pmcp-package/Cargo.toml`.
  </action>
