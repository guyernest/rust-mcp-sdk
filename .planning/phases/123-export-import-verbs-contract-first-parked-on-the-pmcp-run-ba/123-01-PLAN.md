<assumption_delta_decision>
The `assumption-delta scan` fired `pluralization` on this phase. The real delta is not the phrases
it matched — it is D-11: the number of on-disk representations of "a package" went from ONE (the
OCI layout directory, which every shipped verb operates on) to TWO (a movable `.tar` plus the
working layout directory).

- **The noun that is now primary:** the **OCI layout** remains the identity-bearing form. Package
  identity IS the manifest digest that `pack_server` computes over the layout's blobs, and it is
  what `SubjectVerdict` compares an attestation's claim against.
- **Decision: `add-alongside`.** The tar is added as a pure carriage envelope with no identity of
  its own: it carries the layout's bytes, contributes nothing to the digest, and is discarded by
  `load`/`pull` the moment its contents are verified. Promoting it would give a transport wrapper
  authority over package identity, which is exactly backwards.
- **Accepted debt, and what would force a later promote:** if the platform ever assigns a digest to
  the *tar bytes themselves* — which is precisely the open question A4 raises about
  `getPackageArtifact`'s `payloadDigest` — the tar acquires an identity and this model must change
  to `promote` or to a two-identity model. Plan 02 writes A4 into `portability-v1.graphql`'s
  argument comments as an explicit question for exactly this reason.
- **Suggested (not required) invariant test:** a contract test asserting that the manifest digest of
  a layout is unchanged by a `save` -> `load` round trip, i.e. that tarring contributes nothing to
  identity. Plan 04's framing-rule work is the natural home if the executor wants it.
</assumption_delta_decision>

**`artifact.rs` — the codec, and the ONLY module in the repo that names `tar::`.** Write it as a
dependency-light leaf: `tar`, `anyhow`, `serde_json`, `pmcp_package` and `std` only. No `clap`, no
`GlobalFlags`, no `crate::commands::*`, no `reqwest` — it is mounted into the lib target (below) and
must compile there on its own, exactly as `kind.rs` does. Two functions, split on the D-06 boundary:

- `read_verified(tar_bytes: &[u8]) -> Result<VerifiedArtifact>` — parses entries into memory, runs
  every framing and integrity gate, and touches the filesystem ZERO times. Returns an owned
  `VerifiedArtifact { index_json: Vec<u8>, blobs: BTreeMap<String, Vec<u8>> }` keyed by the hex digest.
  For the tracer, the gates that must already be live are: the entry path must be exactly `oci-layout`,
  `index.json`, or `blobs/sha256/<64 lowercase hex>`; anything else is refused by name. Task 3 adds
  the hostile-input gates.
- `write_layout(artifact: &VerifiedArtifact, dest: &Path) -> Result<OciLayout>` — reached only after
  `read_verified` returned `Ok`, so it performs no validation of its own. It calls `OciLayout::create`
  (which writes the `oci-layout` marker and an empty index), then `write_blob` per blob, then
  `write_index` with the deserialized index. Every destination filename comes from `describe_blob`'s
  digest over bytes this code holds — the archive's own path strings are a lookup key during
  validation and never a filesystem destination.
- `write_tar(layout: &OciLayout, dest: &Path) -> Result<()>` — the `save` half. Emits entries in a
  fixed order: `oci-layout`, then `index.json`, then every `blobs/sha256/<hex>` sorted
  lexicographically by hex. Build each `tar::Header` by hand and normalize it so the output is
  reproducible: mtime 0, uid 0, gid 0, empty username and groupname, mode 0o644, regular-file entry
  type, and no PAX/GNU extension records (keep every path short enough that none is needed). Emitting
  the layout marker is deliberate (RESEARCH Pitfall 7): a plain extraction of the tar then yields a
  valid layout for a human debugging by hand, and readers accept-but-ignore it and always regenerate
  it via `OciLayout::create`.

The module header must state, in its own words: that the whole-archive extraction path is never used
because the design makes an archive-supplied destination unrepresentable rather than filtered; that
`cap-std` is deliberately absent because the TOCTOU class it defends is unreachable when no archive
path is written; and that the byte caps Task 3 installs are the resource-exhaustion half.

  <behavior>
    - An entry whose path contains a `..` component is refused, and the destination is unwritten.
    - An entry whose path is absolute is refused.
    - An entry whose type is a symlink, hardlink, directory, fifo, character or block device is refused — only regular files are admitted.
    - An entry nested under a wrapper directory (for example a leading `package/` component) is refused, because the framing rule places `index.json` at the archive root.
    - Two entries with the same path are refused as a duplicate, naming the path — not merged last-wins.
    - A blob whose bytes do not hash to the hex in its own file name is refused, naming the blob.
    - A tar with zero entries, a tar with `index.json` and no blobs, and a zero-byte input each fail with a distinct message.
    - A single entry whose header declares a size over the per-entry cap is refused without allocating past the cap.
    - A tar whose cumulative entry sizes exceed the total cap is refused without allocating past the cap.
    - After ANY of the above refusals, a destination directory that did not exist before still does not exist, and one that did exist is byte-for-byte unchanged.

  <action>
Complete `read_verified`'s gate set and install the two byte caps, then prove both with property tests
that run under `cargo test --lib` through the lib mount, plus integration cases in
`tests/package_save_load.rs`.

**The framing gates.** Add a private `classify_entry` that inspects an entry's header BEFORE any of its
content is read and returns a typed slot (`LayoutMarker` / `Index` / `Blob(hex)`) or a named refusal.
It must reject, each with its own message naming the offending path: a non-regular-file entry type
(symlink, hardlink, directory, fifo, char device, block device); an absolute path; any path containing
a parent-directory component; any path that is not exactly the layout marker, exactly `index.json`, or
exactly `blobs/sha256/` followed by 64 lowercase hex characters; and a second occurrence of a path
already seen. Do the parent-directory and absolute checks on the raw path components, not on a
canonicalized string — canonicalizing consults the filesystem and this function must not.

Reject a duplicate rather than resolving it. Two entries claiming one path is an authoring bug or an
attack, and last-wins would let a hostile writer append a benign-looking entry to shadow a real one.
Say that in the refusal's own message.

**The byte caps.** Two named constants, each with a rustdoc explaining why the number is that number,
in the shape `capture.rs:20-32` already uses. A per-entry cap and a cumulative total cap. Enforce them
by reading through a bounded reader (`std::io::Read::take` over the entry, with the running total
threaded through), NOT by reading to the end and then measuring — Phase 113 recorded that collecting an
over-cap body before measuring it performs exactly the unbounded allocation the cap exists to prevent,
and a tar header's declared size is attacker-controlled input, an early-refusal optimisation and never
the authority. Refuse on overflow naming which cap tripped and which entry.

**The integrity gate.** After every entry is in memory and before any write, re-derive each blob's
digest with `ManifestDigest::from_bytes` and compare it to the hex in its own archive path. A mismatch
is refused naming the blob. Also require that `index.json` was present at all — an artifact without it
is refused rather than yielding an empty layout.

**Ordering is the invariant, not a detail.** `read_verified` must have no filesystem effect on any
path, success or failure. Enforce it structurally: keep every write in `write_layout`, keep
`write_layout` unreachable except through an owned `VerifiedArtifact` that only `read_verified`
constructs, and state in both rustdocs that this split is the read-side mirror of `pack_server`'s
"a rejected pack adds neither a blob nor an index entry".

**Concurrency, documented rather than claimed.** Add a rustdoc section stating what IS guaranteed —
every blob's file name is a digest of its own content, so no interleaving can produce a blob whose
bytes disagree with its name — and what is NOT: `index.json` is not content-addressed, `load` therefore
refuses an existing destination unless `--force`, and two concurrent `--force` runs into one destination
are unsupported. Do not overclaim atomicity the implementation does not provide.

**Property tests, in the lib target.** Under `#[cfg(test)]` in `artifact.rs`, using the `proptest`
dependency the workspace already carries: over arbitrary path strings, assert that any path
`classify_entry` ACCEPTS, when joined onto a destination root, stays inside that root — i.e. no accepted
path escapes. Assert the complement too: a generated path containing a parent-directory component or a
leading separator is always refused. Add a never-panics property over arbitrary byte slices fed to
`read_verified` (it must return `Ok` or `Err`, never unwind) — this is the same boundary plan 07's fuzz
target campaigns, and having the property here first is what makes that target's invariant meaningful.

**Integration cases.** In `tests/package_save_load.rs`, build hostile tars in-test with the `tar`
