Create `cargo-pmcp/fuzz/fuzz_targets/fuzz_package_artifact.rs` and register it in
`cargo-pmcp/fuzz/Cargo.toml` with the same `[[bin]]` shape the existing targets use.

**The boundary.** Arbitrary bytes go straight into `read_verified` through the lib seam — that is the
real untrusted-input boundary this phase created, and it is the direct analogue of the manifest-parse
boundary `fuzz_package_kind` already campaigns. The target body should be small: take the raw slice,
call the reader, discard the result. Do not pre-shape the input into a valid tar; the point is the
adversarial-bytes path.

**Assert a FALSIFIABLE invariant, and prove it is falsifiable.** The weak version — "it returned `Ok` or
`Err`" — is a tautology that a broken implementation passes. Assert instead something a removed gate can
break: on any `Ok`, every returned blob key is exactly 64 lowercase hex characters and every blob's
content hashes to its own key; and on any input, no filesystem path was created (the reader takes no
destination, so this is structural, but assert the peak in-memory retention stays within the sum of the
declared caps, which a removed cap can falsify).

Prove the falsifiability by RUNNING it: disable the per-entry byte cap and re-run a short campaign,
observe a crash or a violated assertion, restore the cap, observe a clean campaign. Record both runs in
the SUMMARY. An invariant nobody has watched fail is an invariant nobody knows is load-bearing — this
repo has a recorded case of exactly that, where a fuzz campaign stayed green while the gap it was meant
to cover was open.

**Module header.** Copy `fuzz_package_kind.rs`'s structure: the phase and requirement it serves, the
boundary it campaigns, the invariant in one sentence, the threat model IDs it exercises (the tar
traversal, symlink, duplicate-entry and allocation-bomb threats this phase registered), the full run
command, and a quick-smoke command with a bounded total time.

**Run a real campaign, not a build check.** Execute at least 20,000 runs and record the run count, the
elapsed time, the corpus size and that the artifacts directory is empty. Use absolute binary paths when
proving the artifacts directory is empty — this project has a recorded case of a shell proxy reporting a
spurious count for a demonstrably empty directory.

If the nightly toolchain `cargo fuzz` requires is unavailable in this environment, do not fake the
evidence: record that the target and its `[[bin]]` entry are in place, that `cargo +nightly fuzz build
fuzz_package_artifact` was attempted, and exactly what blocked it. A truthful blocked note is worth more
than an asserted campaign.
  </action>

round trip this phase delivers (C-4's EXAMPLE requirement).

**Drive the production seams.** The example packs a real `ServerPackage`, writes a real artifact tar
through `write_tar`, reads it back through `read_verified`, materializes it through `write_layout`, and
unpacks and reports it — all through the shipped functions. Do NOT re-implement any of them, and do not
shell out to the binary. A previous phase in this repo shipped an example that re-implemented the loop it
was meant to demonstrate and it was raised as a finding: an example that drives the real seam BREAKS when
the seam drifts, which is most of its value.

**Narrate the three things a reader needs.** Print, as the example runs: what `save` produces and why it
is a tar rather than a directory (the tar is the movable form, the layout is the working form — D-11);
that verification happens entirely in memory BEFORE anything is written, so a rejected artifact leaves
the destination untouched (D-06); and the slots the target environment must fill, with the environment
variable name and the config path distinctly labelled. Those three are the phase's user-visible claims,
and a reader who runs the example should come away knowing them.

**Be self-contained and offline.** Use `tempfile` for both the tar and the layout destination, clean up
on exit, and touch no network. Pull the config and spec from the checked-in golden fixture directory so
the example needs no scaffolding step.

**Show the refusal too, not only the happy path.** After the successful round trip, corrupt one byte of
the tar in memory, feed it back through `read_verified`, print the refusal message, and print that the
destination is still absent. A demonstration of the verify-before-write invariant is worth more than a
paragraph asserting it — and it makes the security property something a reader can watch happen.

Keep the example's own error handling honest: a failure should print what failed and exit non-zero, not
`unwrap` into a backtrace.
