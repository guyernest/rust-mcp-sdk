Add `discovery_url_candidates` and `issuer_matches_metadata` to `src/shared/oauth_validation.rs`.
Keep the module's constraints: ungated, no `reqwest`/`webbrowser`/`dirs`, `url` and
`crate::error::{Error, Result}` only.

`discovery_url_candidates(issuer) -> Result<Vec<Url>>` implements the spec's normative ordered lists
verbatim (both are quoted in RESEARCH § Code Examples). The rule, stated so the implementation cannot
drift: parse the issuer with `url::Url`; take its path with any trailing slash trimmed; if the
remaining path is non-empty, emit the three path-form candidates in the order above; if it is empty,
emit the two path-less candidates in the order above. The well-known suffixes are
`oauth-authorization-server` (RFC 8414's default, which MCP adopts and which pmcp never tries today)
and `openid-configuration` (OIDC Discovery 1.0's).

Write down in the rustdoc, as the function's reason to exist, that this is an ORDERED PROBE SEQUENCE
and NOT a replacement: RFC 8414 §3.1 specifies insertion for the `oauth-authorization-server` suffix,
OpenID Connect Discovery 1.0 §4.1 specifies appending for `openid-configuration`, and RFC 8414 §5
reconciles them with a fallback order the MCP spec makes a client MUST. Cite the measured Entra ID
result (append 200, both inserted forms 404) as the reason the appended form must remain in the list.
The function derives candidates only; the PROBING (and therefore the network) belongs to the callers
in 116-06 and 116-07 — that split is what makes the MUST-ordered sequence testable offline.

`issuer_matches_metadata(issuer_used_to_build_url, document_issuer) -> bool` is a simple string
comparison with NO normalization — the same rule as `iss`, from the same family of specs (RFC 8414
§3.3 / OIDC Discovery §4.3). Its rustdoc must carry the spec's worked example verbatim: a document
fetched from `https://attacker.example/.well-known/oauth-authorization-server` that contains
`"issuer": "https://honest.example"` MUST be rejected. State plainly why this function exists at all:
without it, AUTH-01's `iss` comparison is anchored on an attacker-chosen value and the whole RFC 9207
check is decorative (RESEARCH Pitfall 1).

Write `tests/oauth_discovery_urls.rs` modelled on `tests/pkce_helper.rs` — a header enumerating the
covered rows, spec-worked-example cases first, then the property block. Assert the ORDERED LIST, never
a single expected URL. Derive the property invariants from the spec text (list non-empty, no
duplicates, appended form always present, host/scheme preserved) rather than restating the
implementation's branch condition. No `#![cfg(feature = "oauth")]` — this tier is ungated.

Add `ApplicationType` and `derive_application_type` to `src/shared/oauth_validation.rs`.

`ApplicationType` is `#[non_exhaustive]` with `Native` and `Web` and a `#[must_use] pub const fn
as_str(self) -> &'static str` returning exactly `"native"` and `"web"`. Those two strings are the wire
values from OpenID Connect Dynamic Client Registration §2 — they are compatibility surface; say so in
the rustdoc.

`derive_application_type(redirect_uris: &[String]) -> Result<ApplicationType>` classifies EACH URI and
requires unanimity:
- Loopback host — `127.0.0.1`, `::1` (including the bracketed `[::1]` authority form), or `localhost`
  — classifies `Native`.
- A scheme that is neither `http` nor `https` (a custom/private-use scheme) classifies `Native`.
- `https` with a non-loopback host classifies `Web`.
- `http` with a non-loopback host is an `Err` — it is neither a permitted native loopback nor a valid
  web redirect.
Empty input, an unparseable URI, and a MIXED classification are each `Error::validation(..)` with a
message naming the offending URIs and the two classifications it saw. D-10 is explicit that a mixed
vector is an ERROR, never a silent pick; the message must make the operator's next action obvious.

The rustdoc must state, per RESEARCH's note on SEP-837, that the spec classifies by application
NATURE while this function derives from `redirect_uris` — the two agree for every case pmcp produces
(pmcp's own DCR call hardcodes `http://127.0.0.1:{port}/callback` ⇒ `native`; a platform
`oauth-proxy` with an https redirect ⇒ `web`), and `DcrRequest::set_application_type` (116-03) remains
the authoritative override. Document the derivation as a heuristic for the common case, not as the
spec's rule.

Write `tests/oauth_application_type.rs` covering every behavior row above, plus a proptest over
single-element inputs asserting no panic. Assert the `as_str()` wire values explicitly — a silent
change from `"native"` to `"Native"` would be accepted by every AS as "unknown value, ignore" and
would fail nothing else.
