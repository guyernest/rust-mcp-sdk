Compose the DCR body at `src/client/oauth.rs:241-257`.

**application_type (D-09/D-10/D-11).** After building the `DcrRequest`, call
`derive_application_type(&request.redirect_uris)?` and write the result through
`request.set_application_type(app_type.as_str())`. Derive from the redirect URIs actually being
registered rather than from `config.redirect_port`, so the value stays correct if the port or the URI
shape changes. pmcp's own call registers `http://127.0.0.1:{port}/callback` and therefore derives
`native`; a platform `oauth-proxy` registering an https redirect derives `web`.

Send it UNCONDITIONALLY, on both eras. `application_type` has been a standard OIDC Dynamic
Registration field since 2014, the spec states plainly that "non-OIDC servers safely ignore the
parameter", and era-gating would require plumbing a protocol era into DCR that — exactly like the
callback in 116-09 — does not exist before an MCP connection is established.

A mixed `redirect_uris` vector propagates `derive_application_type`'s error rather than picking one.
D-10 is explicit that this is an ERROR, never a silent choice.

**grant_types (SEP-2207).** Change `grant_types` from `vec!["authorization_code"]` to
`vec!["authorization_code", "refresh_token"]`. The spec's landed text says clients that desire refresh
tokens SHOULD include `refresh_token` in their `grant_types` client metadata. This is the missing
prerequisite for D-14's refresh work in 116-12 and for D-08's headless mode: an AS that was never told
the client wants refresh grants has every reason not to issue one.

**offline_access (SEP-2207).** Pass the discovery metadata into
`do_dynamic_client_registration` (it is a private method, so the signature change is free) and, when
`metadata.scopes_supported` contains `offline_access`, include it in the request's `scope`. The spec
says MAY, conditioned on the AS advertising it — so the check is the whole point and adding it
unconditionally would be wrong. Do not add `offline_access` to `config.scopes`; compose it into the
DCR body only.

Extend `tests/oauth_dcr_integration.rs` rather than starting a new file: it already has the harness,
and its `Matcher::PartialJsonString` idiom is exactly the mechanism needed — the mock matches only
when the body contains the asserted fields, so a regression that drops `application_type` yields a 501
and a red test. Assert the WIRE BODY, never the in-memory struct: the whole point of D-09's `extra`
carrier is that it produces field-identical bytes, and only a wire assertion proves that.

  <action>
Handle the response half of DCR.

**Echo divergence (D-11).** After a successful registration, read
`response.application_type()` and compare it to what was sent. On divergence, `tracing::warn!` naming
BOTH values and the registration endpoint. NEVER fail the registration: RFC 7591 explicitly permits
the AS to modify requested metadata, and failing here would turn a legal server behavior into an
outage. Treat an OMITTED value as "no echo", not as divergence — the AS is not required to echo.
Record the AS's value where the flow can see it, so a later diagnosis does not need the log.

**Registration rejection (SEP-837 ¶3).** The spec obliges clients to surface a MEANINGFUL error when
registration is rejected, because the most common cause is a redirect-URI constraint tied to the
`application_type`. Today the error path returns a bare status. Compose an error naming: the HTTP
status; the AS's `error` and `error_description` if the body parses as an RFC 7591 error response; the
`application_type` that was sent; and the `redirect_uris` that were sent. Those last two are what turn
"registration failed with 400" into an actionable message, because they are exactly the pair the AS
rejected.

Do NOT implement the spec's optional retry with an adjusted `application_type`. The text says clients
MAY retry; an automatic retry would silently register a client under a different type than the
operator asked for, which is the opposite of surfacing a meaningful error. Record the non-adoption of
the MAY in the plan summary so the choice is visible rather than assumed.

Keep the error message free of raw body content beyond the parsed `error`/`error_description` fields —
the same rule the bounded-read refusals follow, so a hostile registration endpoint cannot use the
error path as an echo channel.

Extend `tests/oauth_dcr_integration.rs` with the six behavior rows. For the divergence-warns case,
assert the registration SUCCEEDED (the observable outcome) — asserting on log output is brittle; if
the recorded AS value is exposed on the flow's result, assert that instead and say so.

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-116-35 | Elevation of Privilege | registering a native loopback redirect under the OIDC default `web` type | mitigate | `application_type` derived from the actual `redirect_uris` and sent unconditionally; asserted on the WIRE body with `Matcher::PartialJsonString`, so dropping it turns the mock into a 501 |
