<objective>
Wire AUTH-01 into the CLI authorization-code flow: build the spec-mandated per-request record before
the redirect, bind the `state` value that is currently an unnamed temporary (D-12), and validate the
callback through the pure tier before the authorization code is ever redeemed (D-01/D-02/D-03/D-04).

Purpose: at `src/client/oauth.rs:712` the CSRF `state` is generated inline as a temporary —
`.append_pair("state", &Self::generate_code_verifier())` — never bound to a variable, so it is not
merely unchecked but STRUCTURALLY IMPOSSIBLE to check. The callback at :697-700 extracts `code` and
nothing else. Shipping RFC 9207 `iss` validation while leaving `state` unvalidatable would be
indefensible in review or in a conformance claim; both defend the same mix-up/CSRF family and both
land on the same lines.

**Complexity budget is a live risk here.** `authorization_code_flow_inner` is already ~150 lines
(`:621-772`) and the PR-blocking `pmat quality-gate --checks complexity` caps cognitive complexity at
25. Extract into helpers and into the pure tier; do not inline.
Output: a validated callback that cannot redeem a code it did not verify.
</objective>

  <action>
Introduce the per-request record and bind `state`.

**Record construction.** Before building the authorization URL, construct an
`AuthorizationRequestRecord` from four values: the expected issuer, the PKCE code verifier, the state,
and the resolved `IssPresence`. The spec requires these to live in ONE per-request record rather than
as separate locals — three locals is exactly how `state` became unbindable in the first place.

Expected issuer is `metadata.issuer` per D-02: the anchor is the value the AS itself published in its
discovery document, not `config.issuer` (a user-typed seed) and not the effective issuer computed at
`:505`. The attack being defended against is "this response came from a different AS than the one
whose metadata I fetched," so the DISCOVERED issuer is the semantically correct anchor. As of 116-06
that value is validated at fetch time against the issuer used to build the URL, which is what makes it
a trustworthy anchor at all.

**State.** Replace `.append_pair("state", &Self::generate_code_verifier())` with the record's state,
generated by `pmcp::shared::pkce::generate_state()`. Reusing the PKCE VERIFIER generator for a CSRF
token conflates two distinct RFC roles; `generate_state()` already exists for this and is already
ALWAYS-covered.

**D-04 override.** Add `OAuthHelper::with_iss_validation(self, presence: IssPresence) -> Self` as an
inherent consuming builder, backed by a new PRIVATE field on `OAuthHelper`. It must NOT be a field on
`OAuthConfig`: that struct is public, all-pub-field and not `#[non_exhaustive]`, so a new field is
`constructible_struct_adds_field` = MAJOR and would break three in-repo literal sites plus every
downstream user's.

Read `PMCP_OAUTH_ISS_VALIDATION` at the CALL SITE inside the flow, never in a constructor — the
I/O-free-construction discipline that D-07 imposes on the store applies here too, so a platform can
supply the policy as a parameter instead of through a process environment. Resolve the three levels by
handing them to the pure `iss_presence_from(env_value, builder, discovery_flag)` from 116-02;
precedence is env > builder > discovery flag. Do not re-implement the precedence logic here.

**Discovery flag.** Route the flow's metadata fetch through
`OidcDiscoveryClient::discover_with_extras` so the RFC 9207
`authorization_response_iss_parameter_supported` value reaches `iss_presence_from`. Keep the existing
private `get_metadata` signature working by adding a sibling (e.g. `get_metadata_with_extras`) and
having the old one delegate and discard, so unrelated callers are untouched. Thread the resolved
`IssPresence` into `authorization_code_flow_inner` as a parameter rather than reading it again inside.

Document the new env var in the `OAuthHelper` rustdoc: name, accepted values, the precedence order,
and the fact that ABSENT means current behavior.

Write `tests/oauth_state_csrf.rs` for the D-12 half: state is generated, appears in the authorization
URL, is bound and retrievable, differs between flows, and (as a source-level assertion mirroring the
house static-invariant habit) is not produced by the verifier generator. The mismatch-aborts-redemption
half belongs to Task 2's integration suite.

  <action>
Make the loopback callback a CALLER of the pure tier, and make redemption unreachable without a
passing validation.

**Carry the whole response.** The `oneshot` channel currently carries a bare `Option<String>` code.
Change it to carry the full raw query string (the component after `?`, undecoded) so the parent task
can call `validate_authorization_response(&raw_query, &record)`. Keep the spawned task thin: parse the
HTTP request line, extract the query, serve the existing success/failure HTML, send the query. Do NOT
duplicate validation inside the task — one implementation, in the pure tier.

The existing `Url::parse(&format!("http://localhost{}", path))` step is fine as a way to isolate the
query component, and `query_pairs()` is the right decoder — RFC 9207 §2.4 REQUIRES the
`application/x-www-form-urlencoded` decode before comparison and it performs it. Do not hand-roll a
percent-decode anywhere.

**Validate before redeeming.** In the parent, call `validate_authorization_response`. Only its `Ok`
branch may reach the token exchange. On `Err`, propagate the typed error and return — the
authorization code is NEVER redeemed. This is the single most important behavior in AUTH-01 and the
`expect(0)` mock on `/token` is what proves it.

**Failure HTML is unchanged.** D-03 says so explicitly. Serve the same bytes as today. And because
the spec forbids acting on or displaying an AS-supplied `error_description` after an `iss` mismatch,
the HTML must not gain any AS-supplied text.

**Complexity.** `authorization_code_flow_inner` is already ~150 lines and cog-25 is PR-blocking.
Extract the callback-listening block into its own private async helper returning the raw query, and
keep validation as a single call into the pure tier. If `pmat quality-gate --checks complexity` still
reports a violation after that, extract further — do NOT reach for
`#[allow(clippy::cognitive_complexity)]`, which is reserved for irreducible parsers and protocol
dispatch and requires a `// Why:` annotation per CLAUDE.md.

Write `tests/oauth_iss_integration.rs` on the mockito harness from `tests/oauth_dcr_integration.rs`,
with `discovery_body` parameterized so the document can set or omit
`authorization_response_iss_parameter_supported`. For every rejection case, assert
`err.is_iss_mismatch()` / `err.is_state_mismatch()` — the stable programmatic discriminator is the
whole reason D-03 exists — and keep any message assertion only as a SECONDARY human-readability check.
Every rejection case must also carry an `expect(0)` mock on `/token` with `assert_async()`.

For the error-response non-disclosure case, plant a distinctive marker string in
`error_description` and assert its absence from both the returned error and the HTML.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → loopback callback listener | Anything on the local machine can hit the loopback port with a forged callback |
| authorization server → callback parameters | `code`, `state`, `iss`, `error*` are all AS-controlled and, under a mix-up attack, attacker-controlled |
| pmcp → token endpoint | Redeeming an unvalidated code is the irreversible step |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-116-30 | Spoofing | authorization-server mix-up (a response from AS-B accepted as AS-A) | mitigate | RFC 9207 `iss` compared against the DISCOVERED `metadata.issuer` (itself anchor-validated in 116-06) before redemption; four table rows plus the reject case are integration-tested |
| T-116-31 | Tampering | CSRF / authorization-code injection into the loopback callback | mitigate | `state` generated by `generate_state()`, bound into the per-request record, compared FIRST; the defect at `:712` (unnamed temporary) is removed and its absence grep-asserted |
