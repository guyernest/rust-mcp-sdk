  <name>Task 1: Ratify the pmcp-package version this phase ships</name>
  <decision>Which version number `pmcp-package` moves to for the four source-breaking changes Phase 122 landed</decision>
  <context>
Phase 122 landed four source-breaking changes in `pmcp-package`, currently at 0.2.0:

- `pack_server` grew a sixth positional parameter (122-02)
- `PinnedRef` grew a fifth public field, breaking every struct literal (122-05)
- `unpack_team` changed its return type to `Result<UnpackedTeam>` (122-07)
- `PackageError` — which is NOT `#[non_exhaustive]` — gained a variant, breaking every downstream `match` (122-03)

The version number that names these is one-way: once published it cannot be withdrawn, and `cargo-pmcp` currently pins the caret `"0.2"`.

This decision is NOT settled by any locked decision in `122-CONTEXT.md`. D-01 rates the signature change one-way but explicitly assigns the release half to a later phase, and `122-RESEARCH.md` Open Question 2 flags the ambiguity about whether Phase 122 or Phase 124 makes the call. Its recommendation is to decide here, because the code change lands here.

Recommendation: **Option A**, with Phase 124 keeping only the publish order, the coverage gate's extension to workspace-excluded crates, and the crates.io tag.
  </context>
  <options>
    <option id="bump-0-3-0">
      <name>0.3.0 — bump the minor and move all seven emitters in this commit (recommended)</name>
      <pros>Under Cargo's 0.x rules `0.2.x` and `0.3.0` are semver-incompatible, so an already-published consumer pinned `^0.2` keeps resolving to 0.2.0 and keeps compiling. The version describes what it contains. Phase 124 inherits only the publish half.</pros>
      <cons>Seven files move: the crate manifest, four consuming manifests, the scaffold template constant, and both pin tripwires' constants — including `crates/pmcp-openapi-server/tests/pmcp_package_pin.rs`'s `EXPECTED_VERSION_LINE`, currently the literal `0.2.`</cons>
    </option>
    <option id="bump-0-2-1">
      <name>0.2.1 — bump the patch and leave every pin on the 0.2 caret</name>
      <pros>Cheapest diff: only the crate manifest moves, and no tripwire fires.</pros>
      <cons>`^0.2` resolves to the HIGHEST matching version, so every already-published consumer of `pmcp-package 0.2` picks up 0.2.1 on its next `cargo update` and fails to compile against the four breaks. This is exactly the "CLI pinned to a package version it cannot read" hazard Phase 124's SC3 names, arriving from the opposite direction.</cons>
    </option>
    <option id="defer-to-124">
      <name>Defer the version decision and all propagation to Phase 124</name>
      <pros>Keeps this phase purely about attestation carriage; Phase 124 already owns the release.</pros>
      <cons>The source breaks sit on `main` under a version number that does not describe them, and Phase 124 inherits the seven-emitter propagation work without this phase's context.</cons>
    </option>
  </options>
  <resume-signal>Reply with `bump-0-3-0`, `bump-0-2-1`, or `defer-to-124`.</resume-signal>
