Create `scripts/release-version-sweep.sh` as a permanent, committed, **reporting-only** tool
(the discretion CONTEXT leaves open resolves to permanence: it is ~40 lines, adds no
dependency, and is the only mechanism that can detect a phantom delta — a failure class this
repo has now hit at least seven times).

Header: follow the `scripts/lint-plan-verify-commands.sh` convention — a numbered rationale
block stating (1) what a phantom delta is: a crate whose in-tree version equals its published
version while its source has moved since that version was published, so `release.yml`'s
already-published skip makes it silently not ship; (2) why the published-version oracle is
the crates.io API v1 and not Cargo — `cargo search` and `cargo info` report the in-tree path
override as published state, measured on this repo during Phase 122; (3) why a `User-Agent`
header is mandatory — without one the versions endpoint returns an empty body and every probe
looks like a fetch failure; (4) why the diff base is the earliest `v*` tag *containing* the
crate's version-bump commit rather than the latest tag or the bump commit itself; (5) why this
script reports and never gates.

Discovery: mirror the coverage gate exactly — root members via `cargo metadata --no-deps
--format-version 1` filtered by `.publish == null`, plus the `crates/*/Cargo.toml` scan for
manifests carrying their own `[workspace]` table, each classified through a second `cargo
metadata --manifest-path` call with the same predicate. Emit name, version and manifest path
per crate. A sweep that cannot see what the gate sees would reintroduce the very blind spot
plan 01 closed.

Published version: `curl` the crates.io API v1 versions endpoint for the crate name with a
`User-Agent` header identifying the tool and a contact address, and take the newest entry.
Note in the header that newest-first ordering is observed rather than documented, so the
parse should tolerate an unexpected shape by reporting a probe failure rather than printing a
wrong number. A failed or empty probe prints an explicit marker in the output — never a blank
that reads like "no delta".

Diff base: derive the crate's version-bump commit with `git log -1 --format=%h -L
'/^version = /,+1:'<manifest>`, then take the earliest `v*` tag containing it
(`git tag --list 'v*' --contains <bump> --sort=creatordate`, first entry). When no tag
contains the bump commit, the crate's current version has never been released and the correct
output is a marker saying the bump ships at the next tag — not an empty delta. Otherwise diff
`<tag>..HEAD` limited to the crate directory (for the root crate, `src/` and `Cargo.toml`)
and print the shortstat.

Output: one aligned line per crate carrying name, in-tree version, published version, the
resolved tag, and the delta. This is a report a human reads, so alignment and a stable column
order matter.

Then add a `release-sweep` Make target in the `lint-plans` shape — a `$(BLUE)` announce, the
script invocation, a `$(GREEN)✓` line — with a comment above it stating that unlike
`lint-plans` this target is deliberately NOT chained into `quality-gate`, because it needs
network access and because a version delta is legitimate right up until a release, so gating
on it would produce false CI failures on every ordinary branch. Add the `.PHONY:` line above
the target.

Do not add `release-sweep` to the `quality-gate` recipe.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| crates.io API -> sweep output | An untrusted remote response parsed into a number the release decision rests on. A malformed or empty body must be reported as a probe failure, never rendered as a version or as no-delta. |
| sweep output -> version decision | The report drives permanent, unrecoverable version-number consumption; the human checkpoint is the control on that boundary. |
| `cargo install` of audit tooling -> local toolchain | Dev-only tooling installed at exact pins; it never enters a published manifest. |
