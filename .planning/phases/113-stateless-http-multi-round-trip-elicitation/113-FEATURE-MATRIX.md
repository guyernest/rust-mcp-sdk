## Two Findings Fixed Before the Matrix Could Be Trusted

Both were discovered by running the matrix, not by review. Both are recorded because they
change how this gate must be invoked in future phases.

### F-1 — The build host had run out of disk (deviation Rule 3)

The first matrix pass failed rows 8b and 8c with:

```
ld: write() failed, errno=28 (No space left on device)
clang: error: linker command failed with exit code 1
```

`df -h` reported **148 Mi available** on a 926 Gi volume; `target/` alone was **132 GB**, of
which `target/debug/incremental` was **36 GB**. The doctest binaries could not be linked, so
4 doctests reported FAILED for a reason that had nothing to do with their content.

**Fix:** `rm -rf target/debug/incremental` — incremental-compilation cache only, regenerated by
cargo on demand, never a source artifact and never tracked by git. No `git clean`, no
`cargo clean`, no source file touched. Freed 36 GB (34 Gi still free after the full re-run).

**Why it matters:** a disk-full linker error surfaces as a *test failure*, not as an
environment error. Read the failure text before believing a red doctest row.

### F-2 — `$(rustup which cargo)` alone does NOT pin the compiler (deviation Rule 3)

The plan mandates the absolute rustup cargo so that a shell alias or tool proxy cannot silently
alter results. That is necessary but **not sufficient**. Invoking the toolchain-local `cargo`
binary directly leaves `RUSTUP_TOOLCHAIN` **unset**, so the `rustc` rustup *proxy* re-resolves
the toolchain **per directory** — and honors `rust-toolchain.toml` files **vendored inside
published crate sources**:

```
$ cat ~/.cargo/registry/src/index.crates.io-*/sqlx-0.9.0/rust-toolchain.toml
[toolchain]
channel = "1.94"

$ cat ~/.cargo/registry/src/index.crates.io-*/dashmap-6.1.0/rust-toolchain.toml
[toolchain]
channel = "1.65"
```

Row 6a (`--all-features --workspace`, which is the only row that pulls `sqlx` via
`pmcp-toolkit-mysql`) therefore failed with:

```
error[E0514]: found crate `sqlx_core` compiled by an incompatible version of rustc
  = help: please recompile that crate using this compiler (rustc 1.94.1 ...)
error: the `-Z unstable-options` flag must also be passed to enable the flag `check-cfg`
error: could not compile `dashmap` (lib)
```

and the log even shows rustup live-downloading a 1.65 toolchain mid-build
(`info: syncing channel updates for 1.65-aarch64-apple-darwin`).

**Fix:** `export RUSTUP_TOOLCHAIN=stable` alongside the absolute cargo. This is the ONLY
invocation that actually delivers what the plan asked for. The normal `make quality-gate` path
is unaffected because the rustup `cargo` *proxy* sets `RUSTUP_TOOLCHAIN` for its children —
which is precisely why this drift is invisible until someone bypasses the proxy.

**Binding for future phases:** the correct incantation is

```bash
export RUSTUP_TOOLCHAIN=stable
C="$(rustup which cargo)"
```

not `$(rustup which cargo)` on its own.

**Caveat honestly recorded:** the drift only bites when a crate carrying a vendored
`rust-toolchain.toml` needs a *fresh* compile. Rows 1–5 passed in the first (unpinned) pass
because their `dashmap` artifact was already cached from a proxy-driven build. Every row below
was therefore **re-run from scratch under the pin**, and the pinned run is the authoritative
record. Nothing in this file is carried over from the unpinned pass.

### Row 6 — the two dev-dependency-free commands, VERBATIM and explained

The hazard: the root crate's `[dev-dependencies]` pull `pmcp-code-mode` and
`pmcp-code-mode-derive`, both of which declare `pmcp = { version = ">=2.2.0", path = "../../" }`.
Under a single `cargo test --all-features` invocation, cargo **unifies** the features those
dev-dependencies request of `pmcp` into the very `pmcp` lib being compiled. A module that only
compiles because some *other* feature happened to be switched on by that unification will still
look green. `--lib` drops every test/bench/example target and therefore the entire
`[dev-dependencies]` graph, which is what makes these two rows honest.

```bash
# (a) breadth — every workspace member's lib under every feature, dev-deps excluded.
#     WOULD HAVE CAUGHT: a `pmcp` module that compiles only because a dev-dependency's
#     feature request unified an extra feature into the lib under test, and any workspace
#     member (mcp-tester, cargo-pmcp, the toolkit crates) broken by a pmcp API change.
"$C" build --lib --all-features --workspace

# (b) depth — the exact deployment feature set, dev-deps excluded, warnings fatal.
#     WOULD HAVE CAUGHT: Phase 113 code that compiles under `full` but not under the
#     narrower `streamable-http` set it actually ships behind — i.e. a missing
#     #[cfg(feature = ...)] on an item that only `full` happens to make reachable —
#     plus any new warning (unused import, dead code) introduced by the phase.
"$C" rustc --lib --no-default-features --features streamable-http -- -D warnings
```

Both exit 0.

**Removed: zero.** `grep -cE '^-pub ' ` over the entire Removed section returns **0** — every
single removed line is a *blanket impl* that disappeared because a transitive dependency

**Changed: two, both non-breaking.** The only entries are:

```
-pub fn pmcp::types::elicitation::ElicitRequestParams::deserialize<__D>(__D) -> ...
```

This is plan 113-02's hand-written `Deserialize` impl replacing the derived one (needed to make
`mode` optional for the v2 implicit form). Only the *generic parameter name* changed, from
serde-derive's `__D` to `D`. A type-parameter name is not nameable by callers and is not part
of the API contract — `cargo semver-checks` agrees, reporting no required update.
