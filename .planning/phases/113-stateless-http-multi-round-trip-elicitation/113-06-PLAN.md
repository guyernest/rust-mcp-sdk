<objective>
Wire the server-side INGRESS half of MRTR: extract `inputResponses`/`requestState` from the
raw request params at HTTP ingress, thread them on the Phase-112 `ProtocolContext`, verify
the token against the live principal and originating request in `ServerCore`, route the
four verdicts per D-15, and surface the decrypted continuation plus the input responses to
the handler through `RequestHandlerExtra`.

Purpose: HTTP-03's "a client retry resumes the operation" is entirely this path. It is also
where the phase's security posture is decided — the conformance suite's
`sep-2322-reject-tampered-state` check fails a server that re-prompts on a tampered token,
while D-04's multi-instance degradation requires exactly the opposite behavior for an
unknown key. The key-id discriminator is what lets both be true.
Output: a MRTR-aware `ProtocolContext`, one shared ingest helper called from both dispatch
sites, new `RequestHandlerExtra` accessors, and a live-HTTP verdict suite.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → dispatch (`params.requestState`) | Attacker-controlled token enters authorization-relevant continuation state |
| client → handler (`params.inputResponses`) | Attacker-controlled response payloads reach business logic |
| auth layer → MRTR binding | The authenticated subject becomes the AAD principal |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-113-01 | Tampering | tampered `requestState` treated as legitimate | mitigate | `Verdict::AuthFailed` → `-32602` JSON-RPC error, handler never invoked; test asserts no `result` key and no `input_required` (conformance `sep-2322-reject-tampered-state`) |
| T-113-02 | Spoofing | cross-principal replay | mitigate | Binding principal is `AuthContext.subject` only — never `_meta.clientInfo` (self-reported, optional since spec PR #3002) and never a session id (absent on v2); `principal_mismatch_errors` is the test |
| T-113-03 | Elevation of Privilege | same-principal replay onto different tool/arguments | mitigate | `salient_param_digest` is computed from the TYPED live request that dispatch will execute, not from any client-echoed copy, and lives in the AAD; `originating_request_mismatch_errors` covers both the args and the method case |
| T-113-06 | Spoofing | identity fallback to a session id when unauthenticated | mitigate | The principal expression has exactly one source and one documented fallback (the empty string); no session-id branch exists in the code path |
| T-113-10 | Information Disclosure | verdict discrimination oracle in error text | mitigate | One generic client-facing message for every `AuthFailed` cause; the discriminated reason is `tracing::warn!`-logged server-side only |
| T-113-22 | Elevation of Privilege | unauthenticated deployment collapsing all callers into one principal | accept | An unauthenticated server has no principals to separate; documented in the helper's rustdoc, and TTL + originating-request binding still apply. Phase 114 TASK-05 owns the strict fail-closed owner-binding for Tasks |
| T-113-23 | Tampering | `input_required` leaking onto a method the spec forbids | mitigate | `mrtr_ingest` short-circuits on `!mrtr_eligible(method)`, so a `requestState` on any other method is inert; `request_state_on_non_mrtr_method_is_ignored` is the test (plan 09 adds the exhaustive egress tripwire) |
| T-113-24 | Tampering | unvalidated `inputResponses` reaching business logic | transfer | Surfaced through an accessor whose rustdoc states it is CLIENT-SUPPLIED and untrusted and must be schema-validated by the handler via the existing `jsonschema` path |
</threat_model>
