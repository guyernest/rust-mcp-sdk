- `sep_2322_elicitation_incomplete_then_complete` — `tools/call` → `input_required` with an
  `elicitation/create` entry; retry with `inputResponses.<key>` → complete.

  `inputRequests` and `requestState`.
- `sep_2322_multiple_inputs` — multiple `inputRequests` of DIFFERENT kinds in one result,
  all answered in one retry.
- `sep_2322_multi_round` — THREE rounds with an EVOLVING `requestState`; assert each round's
  token differs from the previous one.
- `sep_2322_missing_response_rerequests` — under-supply the responses; assert the server
  returns a NEW `input_required` re-requesting the missing entry rather than an error
  (server obligation 9).
- `sep_2322_non_tool_incomplete_then_complete` — the same flow on `prompts/get` AND on
  `resources/read`.
- `sep_2322_result_type_included` — assert `resultType` is EXPLICITLY present and equals
  `"input_required"` (not inferred from the presence of `inputRequests`).
- `sep_2322_not_on_unsupported_requests` — a handler signalling on `tools/list` produces a
  normal complete result, never `input_required`.
- `input_required_result_capability_check` — a server signalling for `sampling` when
  `_meta.clientCapabilities` declares none returns `-32021` at HTTP 400 with an
  OBJECT-shaped `data.requiredCapabilities`.

Additional wire-shape assertions the conformance suite depends on and which are the single
most likely silent interop failure:
- `mrtr_fields_are_params_siblings` — assert that on the retry the server accepts
  `inputResponses`/`requestState` at `params` TOP LEVEL, and that a request placing them
  inside `params._meta` is NOT treated as MRTR (the operation re-elicits or errors rather
  than resuming).
- `mrtr_retry_uses_different_id` — assert the server accepts a retry whose JSON-RPC id
  differs from the original and echoes the retry's id back.

Assert on concrete JSON paths and HTTP statuses only.
