<objective>
Era-gate the streamable-HTTP transport's session machinery so a v2 request runs
handshake-free and session-free on the EXISTING code path, and add the v2 HTTP status
mappings the spec requires: GET/DELETE → 405, unknown method → 404, header/body rejection
→ 400. v1 behavior stays byte-identical.

Purpose: HTTP-01 is the load-bearing "stateless" requirement. The failure mode RESEARCH
Pitfall 1 names is subtle and total: `stateless()` is a BUILD-TIME config, so a dual-version
server built with `Default::default()` mints session ids for v2 requests unless the era
overrides the config per request. This plan makes the era, not the config, the decider.
Output: one `sessions_active` predicate wired through four sites, the 405/404/400 mappings,
and a live-HTTP acceptance suite that deliberately uses the stateful default config.
</objective>

  <action>
Three spec-mandated status mappings, all era-gated so v1 is untouched.

**405 on GET/DELETE (v2).** GET carries no body, so `_meta` is unavailable and the ONLY era
signal is the `MCP-Protocol-Version` header. Reuse the existing non-panicking
`decode_version_header`: when it returns `HeaderProtocolVersion::V2`, return
`StatusCode::METHOD_NOT_ALLOWED` from `handle_get_sse` and `handle_delete_session` before
any other work — including before session validation, so a v2 GET never touches session
state. Every other header value keeps today's behavior exactly. pmcp is dual-version, so
do NOT remove the routes.

**404 on unknown method (v2).** The spec is explicit: "If the server does not implement the
requested RPC method, it MUST respond with 404 Not Found and a JSON-RPC error with code
-32601." Phase 112's verification recorded pmcp's current behavior as `-32601@200`. At the
POST response-assembly point, when the resolved era is `Era::V2` AND the assembled response
is a JSON-RPC error carrying `error_codes::METHOD_NOT_FOUND`, emit the same JSON-RPC body
with HTTP status 404 instead of 200. Preserve the original request id in the error envelope
(the Phase-112 discover work already established this and HTTP-05 depends on it). Leave v1
at 200.

**400 on the v2 transport error family.** Implement ONE era-gated status mapper at the POST
response-assembly point rather than a per-site status choice: on `Era::V2`, an error whose
code is any of `HEADER_MISMATCH` (-32020), `MISSING_REQUIRED_CLIENT_CAPABILITY` (-32021) or
`UNSUPPORTED_PROTOCOL_VERSION` (-32022) maps to HTTP 400; `METHOD_NOT_FOUND` (-32601) maps
to 404; everything else stays 200. `-32021` is emitted by dispatch (plan 09), not by this
gate, so the mapper must be code-driven, not call-site-driven. Route the Phase-112 gate's
`V2GateOutcome::Reject(code, msg)` cells through `error_codes::HEADER_MISMATCH` for the
missing-required-header and header/body-mismatch cases, and through
`UNSUPPORTED_PROTOCOL_VERSION` with an `error.data.supported` array listing the server's
accept-list for the unsupported-version case. Do not introduce a bare `-32xxx` literal
anywhere: every code comes from the table (Phase-112 VERS-06 rule, still enforced).

**Decode the `Mcp-Name` sentinel before the body cross-check.** The Phase-112 gate compares
the inbound `Mcp-Name` header to the body's logical name verbatim. A conformant client MUST
send a non-header-safe name in the `=?base64?<b64>?=` sentinel form, which would fail that
comparison and 400 a legitimate request. Pass the raw header value through
`crate::types::mrtr::decode_header_value` before comparing, and treat a `None` (malformed
sentinel) as a `HEADER_MISMATCH` rejection. Use the SAME shared codec the client emitter
uses in plan 05 — do not write a second decoder. Also re-point the module's local
`logical_name_key` at `crate::types::mrtr::logical_name_key` (delete the local copy, keep
any local wrapper thin) so the client and server read one table.

Add `#[cfg(test)] mod tests` unit coverage for the pure classifier parts (era → status
mapping, and the sentinel-decoded name cross-check) and leave the live-HTTP assertions to
Task 3.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → HTTP router | Untrusted method, headers and body select the transport behavior |
| session store → request identity | On v1 the session id is an identity carrier; on v2 it must not exist |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-113-06 | Spoofing | identity collapse when `Mcp-Session-Id` disappears on v2 | mitigate | `sessions_active` makes the v2 path hold no session at all, so nothing downstream can accidentally treat a session id as identity; `v2_ignores_inbound_session_id` proves an attacker-supplied session id is inert rather than accepted |
| T-113-08 | Tampering | header/body desync smuggling (WAF sees one method, server executes another) | mitigate | Phase-112 cross-check retained; its reject cell now emits `HEADER_MISMATCH` (-32020) at HTTP 400 so an intermediary sees an unambiguous rejection status |
| T-113-18 | Information Disclosure | v2 GET/DELETE reaching session-store code before rejection | mitigate | The 405 guard runs BEFORE session validation in both handlers, so a v2 GET never touches session state or the event store |
| T-113-19 | Spoofing | v1 regression silently disabling session validation for everyone | mitigate | `sessions_active` returns `true` for `era == None` (not opted in) and for `Era::V1`; `v1_session_unchanged` and the untouched Phase-112 suite are the regression guards |
</threat_model>
