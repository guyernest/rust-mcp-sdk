<objective>
Land the paired `pmcp` core changes that the hosted-agent flow depends on, shipped as the `pmcp` 2.17.0 minor bump (D-04):

1. **D-106-A fix (D-01/D-02):** `Server::run`'s message loop pumps inbound RESPONSES to the peer dispatcher while a tool handler awaits `peer.sample()` / `.elicit()` / `.list_roots()`. Request handling stays serialized — zero behavior change for existing servers.
2. **`sample_with_tools` peer path (Open Question 1):** the server-side peer can return `CreateMessageResultWithTools` (tool_use/tool_result blocks) so a tool-calling agent loop can drive tools through spec sampling. Same dispatch call as `sample`, only the decode target changes.

Purpose: without the response pump the hosted agent deadlocks; without `sample_with_tools` the `SamplingSource` (AGNT-04) can never carry tool calls. Both are additive `pmcp` 2.17.0 changes and must land together for the D-03 real-loop proof.
Output: fixed `Server::run`, new `PeerHandle::sample_with_tools`, real-loop integration test, version bump to 2.17.0, and the cargo-pmcp scaffold-pin (`PMCP_VERSION`) updated in lockstep (D-04 tripwire).
</objective>

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-108-01 | Tampering | receive-loop response routing | mitigate | Responses are routed to the dispatcher by JSON-RPC id via existing `handle_response`; the split does not change id-matching, only removes the blocking await — no cross-request response leakage |
| T-108-02 | Denial of Service | bounded request mpsc worker | mitigate | Request channel is bounded; single sequential worker preserves existing back-pressure/ordering; the fix REMOVES the current deadlock DoS on in-tool sampling |
| T-108-03 | Denial of Service | unbounded pending peer requests | accept | Peer round-trips are already bounded by the in-flight request scope (idle-host limitation, Phase 106); no new unbounded state introduced |
