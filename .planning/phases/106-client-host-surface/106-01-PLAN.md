<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server -> client (inbound request) | A connected MCP server can now push `sampling/createMessage`, `elicitation/create`, and `roots/list` requests that the client answers. This is a NEW inbound attack surface: untrusted, server-controlled JSON crosses into the client's handler code. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-106-01 | Denial of Service | `dispatch_host_request` deserialization of inbound `CreateMessageParams`/`ElicitRequestParams` | mitigate | Typed serde deserialization only; a handler error returns a -32603 JSON-RPC error response, never a panic or connection teardown. Fuzz coverage added in plan 02. |
| T-106-02 | Denial of Service | unknown/unregistered inbound method | mitigate | Unhandled methods return a -32601 method-not-found response and the receive loop continues (connection stays alive) rather than returning Err and dropping the transport. Unit-tested in Task 2. |
| T-106-03 | Elevation of Privilege | server coerces client into an unapproved LLM call | accept (this plan) / mitigate (plan 02) | The approval seam (HOST-04) is defined here (ApprovalCallback/ApprovalDecision on the registry) but invocation lands in plan 02; default is allow. Deferred invocation is intentional and tracked. |
| T-106-04 | Spoofing/Repudiation | capability advertisement not matching registered handlers | transfer (plan 02) | Capability derivation from the registry (HOST-05) is implemented in plan 02; this plan must not add an independent capability setter. |
| T-106-SC | Tampering | npm/pip/cargo installs | accept | No packages installed — additive code within the existing pmcp crate (RESEARCH Package Legitimacy Audit: N/A). |
</threat_model>
